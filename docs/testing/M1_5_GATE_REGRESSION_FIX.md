# M1.5 界面自测门禁回归修复（M2 落地后）

**背景**：M2 Combat Prototype 落地后，M2 自己的 105 条断言与 718 个单元测试全绿，
但 M1.5 的界面自测（`M1_5UiSelfTest`）变红，且**两次干净运行的失败点不一样**：
一次挂在挖掘阶段（20000 帧超时），一次挂在灵敏度线性断言。本文件记录两处的根因、
判定依据、修法与验证，并**登记没能验证的东西**。

一条贯穿始终的约束：**不为让门禁变绿而放宽断言、删断言或改阈值**。本文件里两处容差
改动都是**收紧**（1.0° → 0.05°；硬编码 0.5° → 0.2° 且可推导），理由逐条写在下文。

## 2. 失败一：挖掘阶段 20000 帧死等

### 2.1 根因（一句话）

**M2 让"手持枪械"占住开局热键栏并默认选中，而 M1.5 自测的挖掘阶段没有先把枪换掉 ——
`Player#updateMining` 每步都在 `isGun()` 上提前返回并重置进度，"进度 > 0"永远不会成立。**

产品侧代码（`Player.java:1049`）：

```java
// M2：手持枪械时左键是"开火"，不是"挖掘"（PRD 5.4「使用左键挖掘或开枪」）。
if (inventory.selectedStack().item().isGun()) {
    resetMining();
    return;
}
```

开局装备（`SkyIslandGame.java:750` `grantStartingGear`）：手枪 ×1 → 第 1 格，手枪弹 ×24 → 第 2 格，
`Inventory` 的 `selectedSlot` 默认 0。因此**一进游戏就是"手持枪械"**。

不对称的来源：`M1ScriptedSelfTest` 在 M2 里已经为此长出了 `firstNonGunSlot(Player)`
（`M1ScriptedSelfTest.java:276`），**`M1_5UiSelfTest` 没有获得同样的处理**。

### 2.2 原始日志证据（`tmp/m2_uiregress3.stdout.txt`，干净运行）

```
[02:12:42.525][INFO ] [UI自测] ? 阶段 9/17 按住鼠标左键挖掘：进度推进并破坏方块（输入层 → 物理 → 世界）
[02:12:42.538][INFO ] [提示] 弹药不足
[02:12:47.552][INFO ] [提示] 弹药不足
[02:12:52.552][INFO ] [提示] 弹药不足
        ...（每 5.0 秒一次，共 35 次）
[02:15:29.461][ERROR] [UI自测] FAIL · 阶段「按住鼠标左键挖掘：进度推进并破坏方块（输入层 → 物理 → 世界）」
        在 20000 帧内达成条件 — 超时（状态=PLAYING，框架计数=20001）
```

`弹药不足` 这条提示直接坐实了"左键被解释成开火"：它来自 `CombatController` 的空枪分支
（`GunState.ShotOutcome.NO_AMMO`）。也就是说脚本按的是左键、手里是枪、每 5 秒"空枪"一次，
而挖掘进度整段为 0。

### 2.3 为什么它"有时又能通过"——那一次通过是运气

`tmp/m2_uiregress.stdout.txt`（02:08 的另一次干净运行）里同一阶段**通过**了。
把它和失败那次逐条对照，差别不在产品，而在**外部输入**：

```
# 通过的那次（tmp/m2_uiregress.stdout.txt）
  504 |[02:08:18.411]   键事件数           = 8
  506 |[02:08:18.411]   鼠标按键事件数     = 17
  507 |[02:08:18.411]   鼠标移动样本数     = 2399
  508 |[02:08:18.411]   滚轮事件数         = 2          ← 自测从不注入滚轮
  274 |[02:08:14.777] 滚轮事件: offset=(0.00, -1.00)
  275 |[02:08:14.835] 滚轮事件: offset=(0.00, -1.00)
  276 |[02:08:15.386] 鼠标按键: PRESS    button=MOUSE_RIGHT (1)   ← 自测从不注入右键
```

* `injectCursorDelta` **不**增加 `鼠标移动样本数`，所以那 2399 是**真实回调**；
* `M1_5UiSelfTest` 全程不注入滚轮，也不注入右键 —— 这两类事件只可能来自外部；
* 两次滚轮 = `cycleSlot(-2)`：选中槽从第 1 格（手枪）跳到空格，
  `selectedStack()` 变成空栈 → `isGun()` 为假 → 挖掘才开始推进（这就是那次"通过"的全部原因），
  时间上也吻合：`弹药不足` 到 `02:08:13.261` 就停止了，随后进度才有读数。

**结论**：这个阶段此前是"依赖物理鼠标偶然滚一下才会绿"的，属于**假绿灯**；
M2 只把它从"偶发"变成了"必然红"。

### 2.4 改了什么

`src/main/java/com/skyisland/game/M1_5UiSelfTest.java`

1. **挖掘阶段显式声明手里拿的是什么**（第 1 帧）：按**内容**扫描出第一个"不是枪"的槽位
   （新增私有 `firstNonGunSlot()`，与 `M1ScriptedSelfTest#firstNonGunSlot` 同一条规则、
   同样不写死槽号），再走**真实的数字键切槽链路**注入 `GLFW_KEY_1 + slot`（按下沿 + 释放）。
   走真实链路而不是直接改 `inventory`，是因为本阶段断言的正是"输入层 → 物理 → 世界"，
   直接改 inventory 会把其中一段绕掉。
2. **把前置条件本身做成断言**（第 2 帧，按下左键之前）：
   `挖掘阶段开始前手里不是枪械（手持枪械时左键是开火，不会挖掘）`，
   详细里带上槽位、手持物 id 与 `isGun`。开局装备以后再变，会在这里露出来，
   而不是变成一条与挖掘毫无关系的"20000 帧超时"。
3. **超时改成"立刻可诊断的失败"**（新增 `failFast(Stage, String)`）：
   * 手持枪械却还在等进度 → 立即失败，报出手持物；
   * 按下左键后 **300 个逻辑步（5 秒）** 进度仍为 0 → 立即失败，报出手持物、
     射线命中的方块坐标、界面状态（用于区分"没打到方块"与"打到了但不可破坏"）。
   正常实现下"进度 > 0"在按下的**同一个逻辑步**就出现（`updateMining` 先置 0 再加 dt），
   300 步是 300 倍裕量，不会误判。

`MAX_FRAMES_PER_STAGE = 20000` 这个通用兜底保留不动：它防的是"挂死"，
而"前提不可能成立"这类失败现在由上面的看门狗负责，两者职责分开。

## 3. 失败二：`17.280° vs 3 × 6.060°`

### 3.1 两个必须分开回答的问题

**(a) 测试设计缺陷（确定存在，算术上不可能自洽）**

原文（改前 `M1_5UiSelfTest.java`）：分量容差 `YAW_TOLERANCE_DEG = 1.0`（度），
线性断言却是硬编码的 `|Δ15 − 3·Δ05| < 0.5`。

设 `Δ15 = 18 + e1`、`Δ05 = 6 + e2`，`|e| ≤ 1.0`，则
`|Δ15 − 3·Δ05| = |e1 − 3e2| ≤ 1.0 + 3.0 = 4.0`。
也就是说**分量断言允许组合差异合法地达到 4.0°，而线性断言却要求 < 0.5°** ——
这条断言比它自己的分量断言还严 8 倍，任何"两个分量各自合规"的情形都不保证它成立。
它是**推不出来**的阈值，不是被放宽的问题。

**(b) 真正需要查清的：投递的像素量为什么是 96 和 101 而不是 100**

先把算术摆清楚（基准 0.120 度/像素）：

| 子检查 | 实测 | 反解出的投递像素量 |
|---|---|---|
| 灵敏度 1.5 | 17.280° | `17.280 / (1.5 × 0.120)` = **96.0** |
| 灵敏度 0.5 | 6.060° | `6.060 / (0.5 × 0.120)` = **101.0** |
| 反转 Y（同一次运行） | 12.960° | `12.960 / (1.0 × 0.120)` = **108.0** |

三个都是**整数**：说明产品的换算率**分毫不差**（0.18 / 0.06 / 0.12 度/像素），
错的只是"这一段窗口里到底收到了多少像素"。

### 3.2 判定：**产品侧输入分配正确；错的是测量窗口没被隔离**

判定依据（三条独立证据）：

1. **产品换算逐位精确，已有单元测试守着。** `PlayerLookSensitivityTest`
   （`halvingTheSensitivityHalvesTheTurn` = `-6.0 ± 1e-9`、`changingTheSensitivityTakesEffectImmediatelyWithoutRestart`
   = `-18.0 ± 1e-9`）与 `FrameInputQuantitiesTest`（`100 px` 进 → `100 px` 出，
   一帧多步只施加一次、零步不丢）走的是与运行时**同一条链路**
   （`InputState.injectCursorDelta → InputMapper.poll → Player.step → Camera.addLook`），
   `clean test` 718 例全绿。也就是说"产品把 100 px 变成 18°/6°"这件事本身没有争议。
2. **多出来的像素只能来自另一个写入方。** 累加器 `InputState#frameDeltaX/Y` 有两个写入方：
   `injectCursorDelta`（自测）与 GLFW 回调 `onCursorPos`（真实鼠标）。产品不会**凭空造**像素，
   所以 96/101/108 里的差额（−4 / +1 / +8）只可能来自真实鼠标。
3. **产生这组数字的那次运行确实有大量外部鼠标输入**（见 §2.3）：`鼠标移动样本数 = 2399`、
   滚轮事件 2 次、右键 PRESS 2 次 —— 这些都不是自测注入的。同一次运行的挖掘阶段也是靠
   外部滚轮"救活"的。**换句话说，那是一次"有人/有进程在操作鼠标"的运行，三个测量窗口
   各被掺进几像素。**

因此结论是：**不是自测记账错误，也不是产品输入分配错误，而是"自测把自己的注入与环境输入
混在同一个累加器里、无法分离"这一测量隔离缺陷。** 历史上第一次测出 18.000/6.000/12.000
（`docs/testing/M1_5_FRONTEND_SETTINGS_REPORT.md` 第 81/165 行）时机器是安静的，
所以是分毫不差的整数值。

### 3.3 改了什么（两处都是收紧）

1. **把测量窗口做成"可对账"的，而不是"默认干净"的。**
   新增宿主接口 `cursorPixelsAccumulatedX/Y`（实现只读
   `InputState.stats().totalMouseDeltaX/Y`，**不新增任何产品侧字段**）。
   每次注入前记一个基准，等满 2 个逻辑步后再读一次，差值就是**这一窗口里实际投递的像素量**；
   与"脚本注入的 100 px"逐位比对：
   * 相等 → 窗口干净，进入断言；
   * 不等 → **判定为环境鼠标输入，作废重测**（最多 `LOOK_MAX_ATTEMPTS = 5` 次）；
   * 重试用尽 → 失败，且失败信息**点名"环境鼠标输入"**并给出投递量/注入量，
     不再表现为一条看似"灵敏度算错了"的读数。
   **为什么是重测而不是放宽容差**：放宽容差会把"产品当真算错了"一起放过；
   重测只要拿到一个干净窗口，断言就仍然是**逐像素严格**的。
2. **容差收紧并给出推导。**
   * `YAW_TOLERANCE_DEG`：`1.0` → **`0.05`**。理由：这条链路是纯算术
     （像素 × 换算率），在干净窗口里残差只有浮点舍入（量级 1e-15 度）；
     0.05° 在 1.5 倍下相当于 0.28 px，仍比舍入宽 13 个数量级，却比原来严 **20 倍**。
   * 线性断言：硬编码 `< 0.5` → **`LOOK_LINEARITY_TOLERANCE_DEG = 4 × YAW_TOLERANCE_DEG = 0.2°`**，
     推导写进常量注释（`|Δ15 − 3Δ05| = |e1 − 3e2| ≤ (1+3)·δ`）。
     0.2° 在数值上**比原来的 0.5° 更严**，且现在是"由分量容差推导出来的"，
     不再是与分量断言互相矛盾的一条硬编码。
3. **期望值从常量推导**（`基准换算率 × 灵敏度倍数 × 注入像素量`），不再在断言里写死
   `18.0 / 6.0 / 12.0`，避免两处数字将来漂移。
4. 摘要新增一行 `ui_selftest_look_contaminated_windows = N`（本次三次运行均为 0），
   供报告直接引用"测量窗口是否被污染"。
