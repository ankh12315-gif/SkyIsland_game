## 4. 性能实测

### 4.1 原始数字（run C，真实输入路径，统计窗口 7.984 s）

| 指标 | 值 |
|---|---|
| FPS | **3232.38** |
| TPS（逻辑步率） | **60.12**（目标 60） |
| mean 帧时间 | 0.31 ms |
| **p95 帧时间** | **0.758 ms** |
| p99 帧时间 | 1.292 ms |
| max 帧时间 | 2.952 ms |
| > 50 ms / > 100 ms / > 150 ms 卡顿 | **0 / 0 / 0** |
| 逻辑步超时（overruns） | 0 |
| 窗口尺寸变化次数 | 0 |
| **`perf_gate_met`** | **true** |

### 4.2 归因

- 与 M1 的 0.685 ms 同量级（本轮 0.758 ms，差异在 10% 以内，属运行间噪声；
  run B 本轮实测 0.623 ms，比 M1 那次还低）。**M1.5 的三处改动（动作表查询、帧级量暂存、
  裂纹叠加层）没有可测量的性能代价**，理由分别是：动作表查询是 12 次哈希/数组查表；
  帧级量暂存只在一帧内搬运 3 个 double、零分配；裂纹叠加层**只在挖掘时绘制**，
  每帧最多 1 次 draw call / 60 个三角形 / 1.7 KB 上传。
- run C 中 `crack_draw_frames = 0`（无人挖掘），因此该运行的测量条件**不因新绘制路径而改变**
  —— 这是"叠加层不污染性能门禁"的直接凭证；run B 中 `crack_draw_frames = 4336`，说明它在
  挖掘阶段确实在画，两行读数互为对照。

### 4.3 对照 §C.4′ 性能测量合同（硬约束，逐条）

| 条款要求 | 本轮落实 |
|---|---|
| 定宽桶直方图、不用平均值代替分位 | 沿用 M1 的 `FrameStats` 实现，未改动（`p95` / `p99` / `max` 全部分列输出） |
| FPS = frameCount / Σ帧间隔（不是帧数÷时长） | 沿用未改，`n=16114` / 窗口 5.0 s → 3233.6（由 Σ 间隔推出） |
| raw 与 clamped 分离 | `clamped_frames = 0`，`overruns = 0` |
| spike 必须做对照实验 | run C 无 spike；run B 的唯一 213 ms spike 与 M1 的 228 ms 同源（同步存档，T-9），**未做任何掩盖** |
| 测量窗口 ≥ 5 s 预热 + 独立统计窗口 | 预热 5.0 s，正式统计 7.984 s |
| 不得为"调绿"而改阈值或缩窗口 | 未改任何阈值；§7.2 专门说明为什么界面自测的 p95 **不用来**判定门禁 |

### 4.4 稳态性能判定

`p95 = 0.758 ms ≤ 16.7 ms` **且** `> 50 ms 卡顿 = 0` → **性能门禁 PASS**（PRD 12.5）。

## 5. 本轮修复清单

### 5.1 帧级输入量错配（★ **真实产品缺陷**，两处症状一个根因）

| 项 | 内容 |
|---|---|
| **症状** | 界面自测里三条与鼠标有关的断言失败：注入 100 px 横移后 Δyaw = **0.000°**、反转 Y 后 Δpitch = **0.000°**、以及 `mouseCaptured` 读数滞后一帧 |
| **根因** | `InputMapper.poll()` 内部的 `consumeFrameDelta()` **一取即清**。主循环是"固定逻辑步 + 可变渲染帧"（`FIXED_DT = 1/60`，`MAX_STEPS_PER_FRAME = 5`），一帧可能跑 **0 个**逻辑步（位移被取走后被静默丢弃）或**多个**逻辑步（同一份位移被重复施加）。120 Hz 渲染 / 60 Hz 逻辑下，约一半的帧没有逻辑步，于是"注入 100 px"有一半概率变成 0 |
| **为什么 M1 全绿却藏着这个 bug** | M1 自测注入的是 `PlayerIntent`（**逻辑步粒度**），绕开了整个输入层；M1.5 的界面自测注入的是**原始键鼠事件**（帧粒度），才把粒度错配暴露出来。**这不是"新引入了 bug"，而是"换了观测方式才发现早就存在"** |
| **修法** | 新增 `FrameInputQuantities`：每帧 `beginFrame()` → `accumulate(lookX, lookY, scroll)`；本帧**第一个真正执行的逻辑步**取走全部并清零，后续逻辑步拿到 `withLook(0,0).withScroll(0)`；菜单期间 `discard()`。`PlayerIntent` 增加 `withLook` / `withScroll`（返回副本，其余 11 个字段逐位保真） |
| **回归守门人** | `FrameInputQuantitiesTest`（8 例：单步施加 / 多步只施加一次 / **零步不丢**（carryover 到下一帧）/ 多帧累积 / discard / 空态 / beginFrame 幂等）+ `PlayerIntentCopyTest`（`withLook`/`withScroll` 不丢字段）+ 界面自测的 3 条 LOOK 断言（等待 ≥2 个逻辑步，比"≥1 步"更严） |
| **修复后读数** | 1.5 倍 → Δyaw **18.000°**（期望 18.0）；0.5 倍 → **6.000°**；反转 Y → Δpitch **+12.000°** |

### 5.2 自测注入相位错位（仪器缺陷，非产品缺陷）

| 项 | 内容 |
|---|---|
| **症状** | ESC 无法触发"暂停"迁移；`mouseCaptured` 断言始终读到上一帧的值 |
| **根因** | 自测脚本原本跑在 `beginFrame()` 里，而 `beginFrame` 在此**之前**已经消费过按下沿。按下沿在帧末被清除 → 注入的键永远等不到消费 |
| **修法** | 自测 `onFrame()` 前移到 `pollEvents()` 的**最前面**（在 `window.pollEvents()` 之前），即"和真实事件同一个相位" |
| **教训** | 注入器与被注入代码的**相位关系**是仪器正确性的一部分。这与 M0 的教训（"测量仪器必须先被验证"）是同一类问题，因此写进本节而不是混在产品缺陷里 |

### 5.3 松键后玩家一直平移（★ **真实产品缺陷**，人工试玩发现，两个根因）

> 用户试玩反馈原文：**"方向键按了一个之后，会一直平移"**。

| 根因 | 内容 | 修法 |
|---|---|---|
| **A. 无输入时水平速度从不衰减** | `Player.applyMovementInput` 开头是 `if (!intent.hasMovement()) return;` —— 松键之后直接返回，`targetVx/targetVz` 停留在最后一次的行走速度，指数逼近永远朝它收敛，于是玩家**永久平移** | 无移动输入且在地面时把目标速度设为 0（靠既有指数逼近收敛到静止）；**空中保持动量**（滑翔感）；有输入时照常归一化方向 |
| **B. 失焦不释放按键** | GLFW 只把事件投递给拥有焦点的窗口：按着 W 切走窗口时，**RELEASE 事件被投递到别的窗口**，本进程的 `keyDown[W]` 永远是 true | `InputState.onWindowFocus(false)` → `releaseAllInputs()`（清空按键/鼠标键 + 清除全部按下沿） |

| 回归守门人 | 断言 |
|---|---|
| `PlayerPhysicsTest` 新增 5 例 | 松键 1 s 后水平速度 `< 1e-6`；**0.25 s 后 `< WALK_SPEED × 0.02`**（手感：不能"停得下来但很肉"）；滑行距离与声明的减速度吻合；空中松键**保留动量**；落地后仍会停；反向输入穿过零点而**不翻到对侧** |
| `InputStateTest` 新增 7 例 | 失焦释放 W / 释放鼠标键 / 清除按下沿；不失焦不释放；失焦保留统计；失焦后可再按；`releaseAllInputs` 可重复调用 |
| 界面自测新增 2 条 | 按住 W 走到 z < −0.5 → 松键 → 等 **30 逻辑步（0.5 s）** → 水平速度 **3.923e-04 格/秒**（阈值 1e-3）；滑行距离 **0.2044 格**（阈值 0.4，远小于一格） |

> **教训（写在这里以免重犯）**：**验证"启动"的断言不能替代验证"停止"。**
> 任何由输入驱动的持续状态（移动、挖掘、加速）都必须有一条"输入撤走之后会收敛"的断言。
> M1 自测 27 项断言里，有"注入 W 后位置 z 变小"，却没有一条看松键之后会怎样 ——
> 这个洞存在了一个里程碑，最后是人工试玩把它挑出来的。
>
> 另一条：阈值必须与**物理时间常数**挂钩，不能拍脑袋取"大约为 0"。
> 指数逼近是渐近的，永远不严格归零 —— 第一版断言写的是 `assertEquals(0.0, speed, 1e-9)`，
> 0.5 s 后残留 `6.57e-8` 而失败。正确做法是把"停下"拆成两条：
> "最终会停"（`< 1e-6`）与"停得够快"（0.25 s 后 `< 2% 行走速度`）。

### 5.4 破坏反馈从未实现（★ **规格缺口**，人工试玩发现）

> 用户试玩反馈原文：**"我长按打碎方块没有动画显示出来打碎"**。

**排查过程（先说结论：不是渲染坏了）**

| 步骤 | 做法 | 结果 |
|---|---|---|
| 1. 查渲染链路 | 读 `HudRenderer.drawMiningBar` + `Player.updateMining` | 逻辑与绘制都正确：进度条 140×5 px、水平居中、`y = 高 − 56` |
| 2. 用像素把它量出来 | 写 `tmp/MiningBarProbe.java`（按绘制契约的填充色 `(242,230,140)` 与轨道色 `(46,46,51)` 做像素扫描） | 两张挖掘截图分别量到 **51/140 = 36.4%** 与 **121/140 = 86.4%**，与同一帧的游戏内读数 `0.361` 一致（**两条独立测量一致到 0.3%**） |
| 3. 查真实鼠标链路 | 发现 M1/M1.5 的自测**从未覆盖"按住鼠标左键"这条路径**（M1 自测注入 `PlayerIntent`，界面自测只注入键盘）→ 新增 `MINE_BY_MOUSE` 阶段 | **链路完全正常**：按住左键 → 进度推进（首次观测 0.0278）→ **37 逻辑步（0.62 s）破坏方块** → 松手后进度归零 |
| 4. 回头查规格 | 对照 `PRD_v0.3.1` §挖掘 | **找到真凶** |

**真凶**：`PRD_v0.3.1` 第 412–413 行明文规定：

| 破坏反馈 | 方块表面显示 **10 段裂纹动画**；每段伴随一次挖掘音效 | **【MVP 必须】** |
| 破坏特效 | 破坏瞬间生成 **8–12 个方块颜色粒子**，播放破坏音效 | 【MVP 必须】（占位）／【Alpha 必须】（完整） |

而 PRD 的 **M1 里程碑交付内容**里也写着"挖掘进度与**破坏反馈**"。
但代码里这两项都不存在，`M1_FIRST_PLAYABLE_REPORT.md §6.1` 的 T-8.1～T-8.8
顺延清单里**也没有登记它们** —— 也就是说，它既没做、也没记账，
属于 `TECH_DESIGN_v0.1.1 §S′` 明确禁止的**"顺延项不得悄悄缩小"**。

> **这解释了为什么"三条断言全绿"仍然让玩家觉得没反馈**：断言证明的是"挖掘逻辑对"，
> 而玩家看的是"方块面上有没有东西在动"。两者之间隔着一整个**表现层**，
> 而表现层的验收标准写在 PRD 里，不在断言清单里。

**本轮的处理（按用户裁决：补最小视觉反馈，不含音效）**

| 项 | 内容 |
|---|---|
| 新增 | `com.skyisland.render.mesh.CrackOverlay`：10 段裂纹贴在命中面上，段数由进度决定（`ceil(progress × 10)`），从面中心向外放射 |
| 为什么不用纹理 | M1 的 T-8.1 已裁定"无 `TextureArray`，用顶点色占位"。因此裂纹用**世界空间小四边形 + 深色 + 混合**实现，不引入任何新资产，也不改顶点格式（沿用 `voxel.vert` 的 `aPos(vec3)+aColor(vec4)`） |
| 图案为什么稳定 | 位置种子 = `hash(blockX, blockY, blockZ)`，全部整数运算 → **同一方块永远同一图案**（不闪烁），不同方块图案不同（不雷同），且零存储 |
| 精度处理 | 顶点只放**块内相对坐标（[0,1]）**，命中方块的 `(blockX, blockZ)` 走 `uChunkOffset` uniform —— 与既有顶点着色器"只给 x/z 加偏移"的约定一致，避免大世界坐标下的抖动 |
| 面朝向怎么来 | 直接读 `RaycastHit.faceNormal*`。技术约束文档早已写明该字段是"供放置相邻空格与**裂纹朝向**"用的 —— 即架构本来就预期了它 |
| 防 z-fighting | 贴面沿法线外偏 `2.5e-3` 格（方块边长的 1/400，肉眼不可见但远大于 1 LSB 深度误差） |
| 防越界 | 面局部坐标钳在 `[0.06, 0.94]`，保证裂纹不飘到相邻方块上 |
| 渲染状态 | 不写深度、开混合、**关背面剔除**（单面四边形靠深度缓冲决定可见性；绕序另由单测断言，两道保险） |
| 回归守门人（两道） | ① `CrackOverlayTest` **10 例**：段数映射（0/负/NaN → 0；向上取整使第 1 段在进度 > 0 即出现；1.0 → 10 段；单调不减；上界 10）、退化输入、顶点数、**六个面的贴面位置**、**每面几何法线与面法线一致（绕序）**、图案稳定性、颜色不受面明暗影响、y/x/z 的分量口径<br>② 界面自测新增 4 条：挖掘期间裂纹长到 ≥8 段（实测 **10 段**）、段数**单调不减**、停止挖掘后归零、临近破坏的取证图已取到 |
| **像素级证据** | 写 `tmp/CrackDiffProbe.java`，对"进度 36%"与"进度 86%"两张截图做差分。这两帧**相机相同、世界相同（方块尚未破坏）**，唯一差异就是新长的裂纹。结果：`changed = 4185 px`，只有 **6 个连通分量**，其中 **①3824 px**（裂纹，包围盒 80×165，位于画面中央的方块面）**②350 px @ y=664..668**（正是进度条那一行的增长）**③–⑥ 1–4 px**（"36%" → "86%" 的数字变化）。**除这三类以外一个像素都没变** —— 裂纹被光栅化这件事因此是可直接检证的 |

**未做（已登记为技术债，见 §6.1）**：PRD 同时要求的**挖掘音效**与**破坏瞬间的 8–12 个粒子**。
音效需要引入 OpenAL 与音频设备（技术约束文档规定"程序合成占位音"），属于独立工作项；
粒子的完整规格按 PRD 归属 Alpha。

## 6. Known Limitations / Technical Debt

### 6.1 T-8.9（新增，本报告为登记源头）：破坏反馈缺音效与破坏粒子

| 项 | 内容 |
|---|---|
| **缺口** | PRD_v0.3.1 第 412 行的「**每段伴随一次挖掘音效**」与第 413 行的「**破坏瞬间生成 8–12 个方块颜色粒子 + 破坏音效**」均未实现 |
| **本轮已补** | 10 段裂纹（视觉部分） |
| **未补的理由** | 音效需引入 OpenAL 与音频设备（`technical-constraints.md` 规定用程序合成占位音），是独立的技术接入；粒子的完整规格按 PRD 归属 Alpha |
| **影响** | 挖掘与破坏仍然**只有视觉反馈、没有任何听觉反馈**；破坏瞬间方块直接消失，没有粒子过渡 |
| **归属** | M2（Combat Prototype 需要开枪/命中音效，届时一并接入音频后端最经济） |
| **为什么必须登记** | 这一条之所以变成"人工试玩才发现"，正是因为它**既没做也没记账**。登记的意义是不再让它第二次消失 |

### 6.2 T-9（沿用，未修复）：存档同步写盘阻塞主循环

M1 登记的 T-9 在本轮**依然存在**：run B 的唯一 213 ms spike 即来自退出时的同步存档
（M1 那次是 228 ms）。M1.5 的范围是前段界面，不包含存档异步化，故**未动**。
建议归属 M2 / Optimization。

### 6.3 裂纹是程序合成的占位表现（与 T-8.1 同源）

裂纹是"深色四边形拼出来的放射状划痕"，不是美术意义上的裂纹贴图。
在 T-8.1（引入 `TextureArray`）关闭之后，它应当被替换为真正的裂纹贴图。
当前形态符合 PRD"先用程序生成占位素材"的口径。

### 6.4 明确不在 M1.5 范围内（范围纪律）

枪械、弹药、换弹、怪物与 AI、生命值、饥饿、昼夜循环、掉落物实体、合成服务、
背包与合成界面、音频后端、粒子系统、`TextureArray`、正式 `IslandGenerator`、
动态区块加载、实体系统 —— 以及 §6.1 的音效与粒子。

这些不是"漏做"，而是范围裁定（`TECH_DESIGN_v0.1.1 §S′`）与用户裁决（§5.4）留下的顺延项。
**M1.5 不因"顺手"而扩大范围**；本轮唯一越出"界面与设置"字面范围的动作是补齐 §5.4 的
破坏反馈，其依据是 PRD 的【MVP 必须】与 M1 交付内容，且**经过用户明确裁决**。

### 7.2 为什么界面自测的 `p95` 不用来判定性能门禁

run A 的摘要是 `p95 = 13.600 ms`、`spikes_gt_50ms = 8`、`max = 1315 ms` —— 这些数字
**不是**引擎的稳态性能，原因有二：

1. 该脚本在设置阶段**主动切换 VSync**（这是"开关立即生效"的验证内容）。VSync 打开后
   帧间隔被钉在 ~16.7 ms，p95 自然落在 13–14 ms（四轮实测：13.5 / 13.8 / 14.4 / 13.6 ms，稳定）；
2. 它包含窗口创建、设置写盘、世界创建、存档写盘与 GL 资源释放 —— 这些一次性开销
   本来就不属于"稳态"。

稳态性能只由 run C（真实输入、独立统计窗口、不切 VSync、不存档）判定。
**不修改该脚本、也不把它的数字解释成"性能不达标"** —— 那是把测量口径当橡皮泥。

### 7.3 复现方式

```bat
build-m1.bat

:: run A：界面自测（自动退出，约 6.5 秒）
run-m1.bat -Dskyisland.uiSelfTest=true

:: run B：M1 自测（回归，自动退出，约 14 秒）
run-m1.bat -Dskyisland.selfTest=true -Dskyisland.worldName=m1-selftest

:: run C：真实输入稳态性能（预热 5 s + 统计 8 s）
run-m1.bat -Dskyisland.measureSeconds=8 -Dskyisland.noSave=true
```

每次运行末尾打印 `==================== 测量摘要 ====================`，其中机器可读结论为：
`ui_selftest_result` / `ui_selftest_asserts` / `ui_selftest_failures`（run A）、
`m1_selftest_passed` / `m1_selftest_scope`（run B）、
`p95_frame_ms` / `spikes_gt_50ms` / `perf_gate_met`（run C）。

> 本机 Bash 工具的 shim 不可用（`dirname` / `cd` 报 127），因此证据运行由
> `tmp/run_m15.js` 用 `spawn({cwd})` 驱动，证据目录、日志目录、存档目录、设置文件
> 全部显式指定 —— 两次运行之间不会互相污染设置或存档。

### 7.4 视觉证据

run A 在**每个阶段结束时抓一张帧缓冲截图**（`glReadPixels` → PNG，不经过 OS 输入系统），
落在 `screenshots/`，共 **22 张**（run B 另有 13 张），覆盖：主菜单、设置列表、重绑等待、
重绑冲突对话框、返回主菜单、开始游戏、移动、**挖掘进行中 / 临近破坏 / 破坏瞬间**、
视角灵敏度、暂停菜单、暂停冻结、恢复、保存返回、设置持久化、损坏回退、退出。

对屏幕内容不满足于"看一眼"的部分，另外写了两个**像素探针**（都可重复运行）：

| 探针 | 作用 | 读数 |
|---|---|---|
| `tmp/MiningBarProbe.java` | 按绘制契约的颜色扫描进度条，量出填充比例 | 36.4% / 86.4%，与游戏内 `0.361` / `0.86` 一致 |
| `tmp/CrackDiffProbe.java` | 对两帧做像素差分并做连通分量分析 | 4185 px / 6 个分量，除裂纹、进度条、百分比数字外**无其它差异** |

另外，M1 自测新增了 `aim_down_and_mine-mining` 截图（在进度 5%–100% 之间取帧），
用于在 M1 的链路上同样留下"挖掘进行中"的画面证据。
