## 5. 过程中发现并修掉的真实缺陷

### 缺陷 1（严重）：**玩家的枪在存档里静默消失**

- **症状**：M1 脚本化回归 **27 项断言全绿**，但日志出现两条
  `[告警][BlockRegistry] 非法的 runtimeId=-1（合法范围 0..14）`。
- **根因**：《存档》的快捷栏按**方块**表序列化，而手枪/手枪弹的 `blockRuntimeId()` 是 −1
  （0 是空气、−1 是"不是方块"）→ 被写成 `skyisland:air` → 读档变回空气。
- **修复**：读写两侧改用**物品**表。**向后兼容**由 M2 的"前缀对齐"不变式保证
  （方块物品的 item id 与 block id 相同），老存档照常读得出来。
- **护栏**：新增 `gunAndAmmoSurviveASaveLoadRoundTrip`，并**直接断言 `warnings().isEmpty()`** ——
  那条告警是这个缺陷唯一可见的迹象，必须盯住它。
- **教训**：**"断言全绿"不等于"没有缺陷"。** 本次是靠日志告警而不是靠断言发现的；
  一条无人断言的 WARN 就是一条无人值守的缺陷通道。

### 缺陷 2（必须修，否则 PRD 规则是死代码）：**距离衰减永远不可达**

- **症状**：把怪物放在 45 格外开火，**什么都没发生**。
- **根因**：射线长度取的是"有效射程"（32 格），而 PRD 的衰减规则描述的是
  "**超出有效射程之后**每格 ×0.9" —— 超程目标根本不会被射线碰到，
  整条衰减逻辑（含 20% 下限）永远执行不到。
- **修复**：引入 `CombatController.RAY_RANGE_MULTIPLIER = 2.0`，
  射线 = 有效射程 × 2（0.9³² ≈ 3.4%，早已撞到 20% 下限，再长只增加步进次数）。
- **教训**：**"规格里写了"不等于"代码里跑得到"。** 不可达的规则在测试里长得和未实现一样。

### 缺陷 3：PRD §6.7 的产品口径被实现缺口改写

M1.5 把 HUD 文案从中文改成英文，理由写的是"点阵字模只覆盖 ASCII"。
PRD v0.3.2 §6.7 明文否定这种做法：

> 「不得因为当前字体渲染能力（如现有 `BitmapFont` 仅覆盖 ASCII）而把产品规格降级为英文。
> 展示能力不足属技术实现缺口，由技术侧以"建立 CJK-capable 字体渲染"方式解决，
> **不是改产品规格的理由**。」

M2 因此补上 CJK 点阵字库，并把玩家可见文案改回简体中文（调试 overlay 保持 ASCII）。

### 缺陷 4：`deaths` 在"整 3 秒"边界上会晚一帧

`deathTimer` 靠每步累加 `1/60` 推进，而 `1/60` 在二进制下不精确 ——
累加 180 次的理论结果是 3.0，实测落在 2.9999999999999996。
判据写死 `>= 3.0` 会让"3 秒后重生"变成"第 181 步才重生"。
修复：判据带 `1e-9` 容差（与 `updateSafePosition` 的既有口径一致）。

### 缺陷 5：挖掘进度条标签压在进度条边框上（**已修，待像素探针复验**）

- **怎么发现的**：不是靠测试，是靠一次**针对 M2 字体改动的人工代码核对**（子代理在核对
  "字体垂直统一"是否漏改调用点时逼出来的）。
- **根因**：M2 把行盒从 ASCII 的 7 行统一到 12 行，约定"文本的 `y` = 行盒顶部"，
  ASCII 字形由 `BitmapFont` 居中到行盒第 3..9 行。`HudRenderer` 的挖掘进度条标签
  （`drawMiningBar`）是**唯一**没跟上的调用点，仍在用 `BitmapFont.textHeight`（= ASCII 的
  7 行字形高）当行高，于是把标签底部算到 `y + uiScale`，而进度条外边框顶边在 `y - uiScale`
  —— 两者相叠 **2×uiScale 像素**。`BitmapFont.textHeight` 的注释自己写着"背景框之类的**旧调用点**仍指望它"，
  `lineHeight` 写着"新排版代码应当用这个"，这就是一处漏网。
- **修复**：改用 `lineHeight` 并把整行贴在进度条上方（留 `3×uiScale` 间隙），
  与该文件 `drawWeaponPanel` 的既有口径对齐。
- **状态诚实说明**：改的是纯几何，改动本身已复核；但**尚未经 `MiningBarProbe` 像素契约扫描复验**
  （本次改动与子代理的构建/运行是并行的，不能在对方跑游戏时抢占同一份 `logs/`、`saves/` 与 `target/`）。
  复验在 M2 收口的验证轮里做。

### 缺陷 6：M1.5 的界面自测门禁被 M2 打红 —— 而且它此前是"靠外部鼠标偶然救回来的假绿灯"

- **症状**：M2 落地后 `-Dskyisland.uiSelfTest=true` 变红：阶段「按住鼠标左键挖掘：进度推进并破坏方块」
  **在 20000 帧内超时**，自测提前中止（只跑到 27 条断言，灵敏度子检查根本没执行）。
- **根因**：M2 让 `Player.updateMining` 在**手持枪械时提前 `return` 并 `resetMining`**（`Player.java:1049`），
  而 `grantStartingGear` 让玩家一进游戏就选中第 1 格的手枪 —— 于是这个阶段**在前提上不可能达成**。
  `M1ScriptedSelfTest` 在 M2 里已经为此长出了 `firstNonGunSlot` / `firstBlockSlot` 两个辅助，
  **`M1_5UiSelfTest` 没有获得同样的处理**。这种不对称就是漏改的直接迹象。
  **证据不是推理**：失败那次的日志里有 **35 条 `[提示] 弹药不足`**（每 5 秒一条），来自 `CombatController` 的空枪分支。
- **更值得记的一条**：这个阶段此前之所以是"绿"的，是**外部真实鼠标滚轮**（`cycleSlot(-2)`）偶然把手枪切走了。
  **它一直是一盏假绿灯，只是没人知道。**
- **顺带解开了灵敏度之谜，并推翻了两层错误归因**：
  `Δyaw` 实测 17.280° / 6.060°，反解出的像素量是 **96.0 / 101.0 —— 都是整数**，
  说明产品换算率（0.18 / 0.06 度每像素）分毫不差。
  真正的来源是 **`injectCursorDelta` 与 GLFW `onCursorPos` 共写 `InputState#frameDeltaX/Y`**：
  自测**无法把自己的注入与环境里真实鼠标的位移分开**。那两次运行里 `鼠标移动样本数 = 2399`，
  还夹着 2 次滚轮事件与 2 次右键 PRESS —— 而自测从不注入滚轮与右键。
  所以它**既不是自测记账错误，也不是产品输入分配错误**，两种归因都错。
- **修复**：挖掘阶段显式切到方块物品，并**把该前置条件本身做成断言**；污染窗口**作废重测**（最多 5 次）
  而不是放宽容差；容差是**收紧**的 —— 分量 ±1.0° → **±0.05°**，线性断言硬编码的 `< 0.5` →
  **`4 × 分量容差 = 0.2°`**，推导 `|Δ15 − 3Δ05| = |e1 − 3e2| ≤ 4δ` 写进常量注释。
  （原文那个 0.5 比它自己的分量容差还严 8 倍，是**推不出来**的阈值。）
- **诊断能力也经过了实测**：临时去掉切槽后，**123 帧（2.4 秒）** 就报出
  「前置条件不成立：手里是枪械（`skyisland:pistol`）」，而不是烧掉 20000 帧再给一句"超时"。
- **教训一**：**"绿灯"必须能解释自己为什么是绿的。** 一个靠环境偶发事件才成立的断言，
  和一条恒真断言一样没有价值 —— 而且更危险，因为它看起来是绿的。
- **教训二（环境事实，会再咬人）**：本机跑自测时**必须保持鼠标静止**。
  真实光标回调与注入共用一个累加器，动一下鼠标就会污染读数。

### 缺陷 7（人工试玩第 1 轮暴露）：M2 新增的三个调试键**没有进开局帮助横幅** —— 直接造成"一只怪都没出现"

- **事实**：全项目只有一处告诉玩家调试键是什么 —— `SkyIslandGame.java:899`，写的是
  `F2 截图   F3 调试 overlay   F5 存档   F9 强制重生（调试键，不可重绑）`。
  而 M2 新增的 **`F4` 刷怪 / `F6` 调试补给 / `F7` 清怪**（`SkyIslandGame.java:1044/1047/1050`）**一个都没写进去**。
- **后果不是"少一行字"**：M2 的近战怪**只有 `F4` 这一条产生路径**
  （`EntityManager.spawnMeleeMonster` 的非测试调用点只有 `debugSpawnMonster`），**没有任何自然刷怪逻辑**。
  玩家不知道 F4 → **M2 的怪、咬人、受伤、死亡、重生这一整套内容在人工试玩里根本不可达**。
  实测：108 秒试玩 `entities_total_spawned = 0`、`combat_entity_hits = 0`。
- **归因**：M1 写的横幅在 M2 加了三个键之后**没有同步更新**。这不是实现错误，是**可发现性缺口** ——
  与 G9（开局弹匣为空）属同一类：**功能是通的，玩家找不到它**。
- `F4/F6/F7` 刻意不进可重绑动作表是**对的**（PRD 键位表里没有它们）；
  但"不进动作表"不等于"不该让玩家知道"。**已登记为 G10。**

### 缺陷 8（严重，人工试玩撞出）：**方块破坏后区块网格永不重建 —— "挖掉了但还看得见"**

- **症状**（玩家原话）：「长按鼠标左键打碎方块的时候，方块模型没有消失，但是我确实碰不到它了。」
- **根因**：`renderer.processMeshRebuilds(world)` **只被 `warmUpMeshes()` 调用过一次**。
  换言之，**只有启动预热那一轮会重建区块网格，正式游玩期间一次都不会**。
  世界数据与碰撞已经更新，画面却还是旧网格 —— 于是"看得见、碰不到"。
- **证据（第 2 轮人工试玩，52 秒）**：`blocks_broken = 6`，而 `mesh_build_count = 16`
  —— **16 正是 4×4 区块的预热值，全程一次没涨**；待重建队列从 `队列=0` 一路攒到 `队列=3` 再没下降。
- **为什么一路活到 M2 才被发现**：所有自测都没有对"网格重建计数"下过断言。
  设计文档其实**早就把这条失败模式写进失败模式表**（`TECH_DESIGN_v0.1.md:563`：
  `meshDirty | 方块写入 / 光照变化 → 网格重建队列 | 挖了方块但视觉不变`），
  但 **"文档里写了预警" ≠ "有人登记了它"** —— 这正是本项目第 4 条审计判据。**第三次**由人工试玩撞出。
- **修复**：在 `SkyIslandGame#render(alpha)` 里消费队列，且**必须赶在 `renderWorld` 之前**
  （否则本帧画的还是旧网格）。放在渲染钩子而不是逻辑步，是因为网格要上传到 GL，只有它持有上下文。
- **回归守门人**：`M2CombatSelfTest` 的 `DONE` 阶段新增两条断言 —— "游玩期间网格被重建过"
  （`meshBuildCount` 相对自测开始前增长）与"重建队列未被积压"。
  放在 `DONE` 而不是 `BREAK_PARTICLES` 里，是因为重建由渲染钩子消费，而 `checkBreak()`
  可能与最后一次破坏落在**同一帧** —— 那样"还没轮到渲染"会被读成"没重建"，变成一条偶发红的断言。
  **断言放在哪里，也是一种设计。**

### 缺陷 9（严重，人工试玩撞出）：**一次性输入（右键放置 / R 换弹 / 数字键选槽）被静默丢弃**

- **症状**（玩家原话）：「放置方块无法放置」。
- **根因**：这三件事都是"按下沿"语义，但它们一直搭在 `frameIntent` 上，而 `frameIntent` 是
  **逐逻辑步复用**的。主循环是"固定逻辑步 + 可变渲染帧"，一帧里可能跑 **0 个 / 1 个 / 多个**逻辑步，
  于是同时存在两个方向相反的错误：
  - **零逻辑步的帧 → 静默丢弃**（下一帧 `frameIntent` 被整体覆盖，边沿永远消失）；
  - **多逻辑步的帧 → 重复施加**（一次点击放置两格、一次 `R` 换两次弹）。
- **现场数字**：`样本数_帧 = 34455` 而 `logic_steps = 3518` —— **只有约 10% 的渲染帧带逻辑步**，
  所以大约**九成的右键点击被丢掉**。
  最硬的一条证据是：`blocks_placed = 0` **并且** `placement_rejected = 0`。
  `Player.step` 每个逻辑步都会调 `handlePlacement`，而一旦 `usePressed` 为真，
  **要么 `blocksPlaced++`、要么 `placementRejections++`，没有第三条路**。
  两个都是 0 ⇒ **那一下点击根本没走到放置代码**（走到过就必然留下一条计数）。
- **另外两个走同一通道的输入**（数字键选槽 / `R` 换弹）**由构造决定具有同一风险**，
  但本轮读数**不能给它们定罪**：第 2 轮的 HOTBAR 高亮确实变过（`dirt` → `pistol_ammo`），
  而**滚轮走同一条帧级通道且 M1.5 早已修好** —— 于是"是数字键按成功了、还是滚轮滚的"
  从日志里分不开。这里只声明**同通道 ⇒ 同风险**，**不声明"已观测到它的症状"**。
  这与缺陷 6 的教训是同一条：**绿灯（和红灯）都必须能解释自己为什么是那个颜色。**
- **它属于缺陷 6 那一族**：`FrameInputQuantities` 的类注释**早就写明了这个失败模式**
  （"一帧零个逻辑步 → 静默丢弃 / 一帧多个逻辑步 → 重复施加"），M1.5 也据此修好了
  **视角位移与滚轮**。但那次只覆盖了连续量，**落下了三个离散量** ——
  又是一次"一个自测改了一个没改"（缺陷 6 的原文：这种不对称就是漏改的直接迹象）。
  为什么自测抓不到：自测**按逻辑步注入意图**，注入粒度就是逻辑步，从构造上不存在这个错配。
- **修复**：把三个离散量并入同一条"暂存 → 本帧第一个**真正执行的**逻辑步一次性发放"通道
  （`FrameInputQuantities#accumulateDiscrete` + `apply` 里发放并清零；`discard` 一并清掉，
  这样在菜单里点的那几下不会被带进游戏变成放置）。
  相应新增 `PlayerIntent#withUsePressed / withReloadPressed / withHotbarSlot` 三个 wither。
- **回归守门人**：`FrameInputQuantitiesTest` 新增 5 条（零逻辑步不丢 / 多逻辑步不重复 /
  同帧连点合并 / 选槽同通道 / `discard` 清离散量）；`PlayerIntentCopyTest` 新增 4 条
  （三个新 wither 的字段保真 + `beginFrame` 那一串组合调用互不覆盖）。
  后者守护的是同一类风险：**15 个位置组件手抄一遍，写反了编译器不会说话**。

## 6. 关键技术决策（及为什么）

| 决策 | 理由 |
|------|------|
| CJK 用**离线烘焙 12×12 点阵 + 生成 Java 源文件**，不引 FreeType/STB、不引 PNG 图集 | 与 `BitmapFont` 既有取向一致（零外部资产、无"资产丢失导致 HUD 空白"的失败模式）；完全确定性、可单测；无需新依赖与网络 |
| 生成器**扫描源码**得到字符集，而非手写列表 | 手写列表一定会漏；漏一个字符的症状是屏幕上出现空白而无人察觉 |
| 新增 `CjkFontTest` 做**全库覆盖护栏** | 本次开发中它**四次**当场拦下"新增中文文案却没有字形"，包括最终一次（`U+76EF 盯`） |
| 战斗事件走**监听器接口**，返回 key 而非拼好的文案 | 一步内可同时发生多类事件，塞进一个 record 会得到 20+ 组件的位参数表（`PlayerIntentCopyTest` 防的正是那类错误）；且 PRD 禁止在 UI 代码里散落中文 |
| 瞄准是**派生状态**（持枪 + 右键），不可外部置位 | 否则会出现"手里是泥土、视野 45°"且没有任何路径能改回来 |
| `CombatController` 不依赖 `render` 包 | 玩法单向依赖表现；表现层换实现不影响战斗逻辑，也让战斗可无窗口单测 |
| 实体画成**碰撞箱大小的盒体** | M2 无模型/纹理管线；"所见即所中"优先于好看 —— 不一致的命中判定对射击手感是致命的 |
| 准星高亮复用**开火那一次射线判定** | 准星说"指着怪物"与子弹打到怪物不可能矛盾 |

5. **收尾纪律（四条，都是踩过才写下来的）**：
   - **长任务从冻结 jar 启动**（`SKYISLAND_JAR=<副本>`）。Maven 会就地重写 `target/`，
     而 JVM 惰性读类 —— 并发构建会把正在运行的游戏抽掉。实测两种症状：
     一次是 **20000 帧死等**，一次是 **17 秒变 2 分 37 秒**。
   - **跑自测时保持鼠标静止**。真实光标回调（GLFW `onCursorPos`）与自测的 `injectCursorDelta`
     **共写同一个累加器**，动一下鼠标就会污染读数。
   - **字形生成器排在收尾清单的最后一项**。任何新增中文（**包括注释**）都会让 `CjkFontTest` 变红，
     所以要在所有会插入中文字符的改动落地之后统一重跑一次，而不是每个 worker 各跑一次。
   - **改了通道划分，就要同步改那张画通道的表**。本轮缺陷 9 把"右键放置 / 数字键切槽"从
     意图快照挪到了帧级通道，而类头 javadoc 的动作通道表**还写着旧划分** ——
     文档漂移会让下一个人照着错的表把 bug 改回来。**代码改完先回头看一眼有没有描述它的文档。**
   - **门禁必须在"空存档目录"里跑，而且这件事要由运行器保证，不能靠人记得**。
     本轮实测代价：用同一批 `saveDir` 连跑两次，第二次三个门禁**全红**
     （m1「破坏计数增量=0」、m1「放置位置实际=air」、ui「行走距离 0.000 格」、m2 51 条连锁失败）——
     因为它们**读进了上一轮的存档**：地形已被挖掉、方块已放过、玩家位置是上一轮的。
     **假红最危险的地方在于它长得像真红**：`破坏计数增量=0` 看起来就是一条产品缺陷，
     会让人去改根本没坏的代码。M2 自测自带一条前置条件断言挡住了自己
     （"存档已存在 → 请先清空该目录再跑"），**这次的修法是把同一保证提到运行器层**：
     每次运行开一个带时间戳的新目录（`tmp/gate-runs/<stamp>/<tag>-saves`），
     并在启动前断言目录为空 —— 连删除动作都不需要。
