## 1. 为什么必须有一份真人清单：自动化到此为止

自动化能证明的是「**两把枪的参数不同、状态机正确、存档一致、无回归**」。
它证明不了的是「**一个活人拿起来能立刻分辨出这是两把不同的枪，而且都好用**」——
而这恰恰是 v2 §19 第 14 条的原文要求：

> 14. 真人试玩能明确感知两把枪的差异。

这两件事的分界线必须画清楚，否则会出现最糟糕的一种收尾：测试全绿、门禁全绿，
于是宣称"武器系统泛化完成"，而实际上第二把枪玩家根本没摸过。
Story 9 报告里登记的那个缺口就是它的具体形态 —— SMG 在代码里完整存在，
却在**任何正常玩法路径上都拿不到**。

所以本 Story 的产物是两件东西：
1. 一份**机器已经举证完的对账表**（§3）—— 把 15 条通过标准里"人无需重复验证"的那些钉死；
2. 一份**必须由人去按的清单**（§4）—— 只留真正需要人的判断。

## 2. 本次为试玩做的前置改动：SMG 的获取路径

### 2.1 裁决

主理人 2026-09-27 裁决：**开局装备两把都发。**

理由（复述以便追溯）：合成配方在 M3 之外（`SkyIslandGame:1226` 附近注释明文写
「合成（手枪弹 R11）属 M4 范围」），因此在 M3 里唯一站得住的获取路径就是开局装备，
而 F6 调试补给复用同一个方法，自动同步生效。

### 2.2 改动清单

| 文件 | 改动 |
|---|---|
| `SkyIslandGame.grantStartingGear()` | 手枪 ×1 + **冲锋枪 ×1** + 手枪弹 ×24（顺序决定快捷栏 0/1/2） |
| `Localization.MSG_GEAR_GRANTED` | 「已获得 手枪 + **冲锋枪** + 手枪弹 ×%d」 |
| `M2CombatSelfTest.checkGear()` | 新增 2 条断言：快捷栏第 3 格是冲锋枪（**直接举证 v2 §19-2「SMG 可正常获得」**）、数量 = 1 |
| `M2CombatSelfTest` Stage 标签 | 「开局装备（手枪 + 2 个满弹匣）」→「（手枪 + 冲锋枪 + 2 个满弹匣）」 |
| `SkyIslandGame.grantSmgForSustain()` | **口径收紧**：不再发放，只负责在快捷栏里找到 SMG 并选中；找不到返回 `-1` |
| `SkyIslandGame.releaseSmgAfterSustain()` | **不再清空 SMG 槽位**，只还原选中槽位 |

### 2.3 为什么要连带改那两个自测夹具（这是一次有意的口径收紧，不是顺手清理）

Story 9 时 SMG 不在开局装备里，`SMG_SUSTAINED` 阶段只能**自己发一把、末了再删一把**。
SMG 进了开局装备之后，这套夹具不但多余，而且**有害**：

- 它会把玩家本来就有的那把一起删掉；
- 退出自动存档因此比存档阶段快照**少一把枪** → 「逐格一致」变红，
  而那是**夹具污染**，会被误读成产品缺陷。

改成「只选中、不发放」之后，这个阶段的前提变成一句可说清的话：
**「开局装备给了 SMG」**。这条前提不成立时，它应该变成一条会红的断言
（`smgRuntimeId >= 0`），而不是被静默补发掩盖 ——
否则"玩家拿不到 SMG"这个真问题会再一次被测试藏起来。

## 4. 真人试玩清单（A–H）

> 通用前提：新建世界（不要读旧档），确保开局快捷栏是 **1=手枪 / 2=手枪弹 / 3=冲锋枪**。
> 键位以游戏内「设置 → 键位」为准；下文写的是 M2.2 默认口径。

### A. 手枪：单击 = 单发（对应 §19-3）
1. 按 `1` 切到手枪，对空旷处**快速连点**左键 10 次。
2. **期望**：每次点击**恰好**打出 1 发；弹匣读数每次 −1。
3. **按住不放** 2 秒：**期望**仍然只有 1 发（SINGLE 不吃 `attackHeld`）。
4. 若"点一次打两发"或"点了没反应"：立刻停下，这是输入 latch 的回归，属**阻断级**缺陷。
5. 判定：☐ PASS ☐ FAIL ☐ TODO ______

### B. SMG：按住 = 全自动（对应 §19-4）
1. 按 `3` 切到冲锋枪，**按住**左键 3 秒。
2. **期望**：连续出膛、弹匣从 24 稳定掉到 0（约 2.4 秒打空）。
3. **点一次**：**期望**也是一发（AUTO 同样响应按下沿）。
4. 与 A 对比：同样的"按住"动作，手枪 1 发、冲锋枪一梭子 —— **这是最直观的差异化证据**。
5. 判定：☐ PASS ☐ FAIL ☐ TODO ______

### C. 换弹：两把枪各自的节奏（对应 §19-5）
1. 手枪打空 → 按 `R`：**期望**约 1.2 秒后弹匣回满 12。
2. 换弹**过程中按住 W 走动**：**期望**换弹**不被打断**，走完即完成（M2.2 口径）。
3. 冲锋枪打空 → 按 `R`：**期望**约 1.5 秒（比手枪**明显更久**），弹匣回满 24。
4. 弹匣已满时按 `R`：**期望**提示"弹匣已满"，不消耗后备。
5. 判定：☐ PASS ☐ FAIL ☐ TODO ______

### D. 表现层差异：不看 HUD 也能分辨（对应 §19-8 / §19-14）
1. 按 `1` 与 `3` 来回切换，观察**手上模型**、**背包图标**。
2. **期望**：两者一眼可辨（几何不同：`GUN_PARTS` vs `SMG_PARTS`；图标不同）。
3. 开火时观察**枪口火光位置**：**期望**两把枪的枪口不在同一处（0.55/0.20/0.12 vs 0.72/0.24/0.15）。

### E. 瞄准差异（★M3 试玩可调项）

## 6. 已登记的 TODO / 边界（不阻断本 Story 开跑）

1. **`perf_gate_met` 绝对阈值门禁在本机不可靠**（M1 期遗留）：冷启动 / Windows 调度会
   产生 50–130 ms 尖峰把它打成 false。建议后续改判据为「p95/p99 相对基线」而非「单次 max」。
2. **F6 补给会重复发枪**：`grantStartingGear` 每次调用都发一整套，因此反复按 F6 会
   让快捷栏里出现多把枪（自测里因此出现过 pistol ×2 / smg ×2）。这是既有行为，
   在 M2.2 就这样；若觉得该改成"只补弹药、不补枪"，属产品变更，需主理人裁决。
3. **可选 follow-up：JFR allocation profiling** —— Story 9 的「SMG 连发无 per-shot 新分配」
   目前是**代码审查 + 计数证据**，不是 JVM 分配采样。
4. **两把枪共用一种弹药**是 v2 §6.1 的明文决定（"M3 只需要一种实际弹药"），
   不是偷工减料 —— 若试玩认为必须分弹药，那是设计变更，不在 M3 范围。
