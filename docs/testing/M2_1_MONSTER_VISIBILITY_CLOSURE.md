## 0. 一句话结论

「看不到怪物」的根因**不在刷怪，而在渲染**：`EntityRenderer.buildMonsterVertices` 给 `Boxes.write` 传的 pivot 是 `pivotX, 0.0, pivotZ` —— **pivotY 被硬编码成 `0.0`**，而 `MonsterModel` 产出的是**局部**坐标（原点＝脚底）。于是怪物的**世界 Y 恒等于局部 y**，与其实体位置无关：玩家脚底 y=64 时，怪被画在**脚下 62.2 格的地下**。

模拟侧一切正常 —— 它会追你、咬你、把你咬死，只是**画在屏幕外**。11:52 那次真人试玩的日志是完整的现场：怪生成在 `(3.49, 64.00, 12.93)`「相对玩家 下方 0.0 格」，随后 **11:52:50–56 连咬 5 口把玩家 20→0 血咬死**（水平 1.31–1.59 格、垂直 Δy 0.00 格）。

按用户 §7 给出的判据 —— *entity exists + position valid + frustum = true + LOS = true 但屏幕像素中不存在 ⇒ RENDER BUG* —— **判定为 RENDER BUG**。

## 3. F4 产品语义重定义（§3）

落点从「含俯仰的 3D `camera.forward() × 5`」改为**候选搜索**：

2. 沿它取候选 t ∈ {4.0, 4.5, …, 8.0}（9 个，**就近优先**）；`SPAWN_CANDIDATE_MIN/MAX/STEP = 4.0/8.0/0.5`；

4. 候选必须**同时**满足四条硬条件，否则 `continue` 下一个；

## 11. 缺陷 D12 的根因与三重假阳性

**根因**：`EntityRenderer.java` `buildMonsterVertices` 传 `pivotX, 0.0, pivotZ`。契约在两处 javadoc 里**写得很清楚** —— `MonsterModel`：「原点 = 实体**脚底中心**」；`Boxes.write`：「**怪物：pivot 取实体脚底中心（世界偏移已减），局部 y 直接就是绝对高度**」。

**三重假阳性叠在一起**（这是它长期存活的原因）：

1. **断言单边**：`MonsterModelTest#rotatedPartsStillFitInsideTheCollisionBox` 原本算 `dy = out[i+1] − SURFACE_FEET_Y` —— **把渲染器漏掉的那一项减掉了** —— 然后只断言**单边上界** `worstMaxY <= 1.80`。缺陷把几何整体压低 62 格后 `worstMaxY ≈ −62.2`，单边上界**恒真**：它只能抓「太高」，抓不到「太低」。
   *（负向对照 `tmp/nc_pivot_y.txt`，改回 `pivotY = 0.0` 后新断言变红：`实测最低 -64.00051111262292，下界 -0.03`。）*
2. **截图不看内容**：`M2CombatSelfTest` 在怪应正对镜头时 `requestScreenshot("monster-in-view")` —— 验收条件被写成「**拍下**这张截图」，而不是「这张截图**里有怪**」。
3. **顶点数 ≠ 像素**：其余断言全是「盒体数 = `PART_COUNT`」「写出的 float 数正确」—— 提交了多少几何，不是屏幕上有多少像素。

**与缺陷 8/9 同族**：契约**明明写进了 javadoc**，却没有任何断言登记它。第 4 条审计判据（「技术文档里的预警 ≠ 登记」）**第四次成立**。

修复后新增的世界 Y 断言是**双边 + 存在性**的：`worstMaxY <= 1.80`（头不戳出碰撞箱）**且** `worstMinY >= −0.03`（脚不沉到脚底以下）**且** `worstMaxY >= 1.5`（确实有部件在顶部，防止「整只塌到脚底」也能满足上界）。
