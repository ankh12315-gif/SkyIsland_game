## 0. 一句话结论

PRD 4.2 的岛屿布局表此前**只存在于文档里** —— M1–M5 一直在跑 `TestWorldGenerator`
那块 64×64 测试平台（高台 / 楼梯 / 虚空坑 / 跨区块玻璃板）。
它是**玩法机制的自测夹具**，不是产品世界。本轮把产品世界补上，
并用 13 条断言把布局、密度、种子、出生点可达性逐项钉死。

过程中抓到 **4 个真缺陷**，其中两个（整数除法、多种矿分配方式）都属于
"看起来完全正常、但产品行为是错的"那一类。

## 2. ★ 本轮抓到的 4 个真缺陷

### 缺陷 1：轮廓判据里的**整数除法**（最隐蔽）

```java
// 错
double nx = (wx - island.centerX()) / island.half();
// 对
double nx = (double) (wx - island.centerX()) / island.half();
```

Java 的 `int / int` 是整数除法。`island.half()` 返回 `int`，于是 `nx` 只会取到
`0` 或 `±1`：`(-15) / 16 == 0`。

**后果**：岛屿轮廓退化成「完整方块 + 只切掉 `(-16,-16)` 一个角」。
探针实测 `main columns = 1023 / 1024` —— 1024 列里只有 **1 列**落在 `d > 0.94` 的带内。

**为什么它能活这么久**：岛确实是方的、确实有种子参数、确实有厚度，
单看任何一张截图都完全正常。唯一露馅的是"两个不同 seed 生成逐格相同的世界"，
而这条在没有专门断言时**根本没人会去查**。

> 这是本项目第 5 次撞上「断言全绿 ≠ 没有缺陷」的同族问题。
> 上一批是 M2 的枪在存档里静默消失（27 条断言全绿，日志里两条无人断言的告警）；
> 再往上是 M2.1 抓出 8 处"已定义、从未被调用"的死代码。

### 缺陷 2：多种矿**各自抽签** ⇒ 谓词与产物分叉

第一版对每种矿各自判一次 `hash < 0.5`，于是**同一格可以同时被判成煤和铁**。
而 `oreAt` 按 `Ore.values()` 顺序返回**第一个**命中的 —— 实际落盘的只有煤。

**症状**：金属岛铜，谓词说 40 格、世界里只有 37 格，多出的 3 格恰好落在
"煤也命中"的位置上。

**它为什么难查**：它**不会**让任何一条"密度是否达标"的断言显眼地变红，
只让某些矿看起来"偏少"。于是极易被当成"参数没调好"而反复调密度 ——
而真因是**分配方式**。本轮我确实先怀疑了密度参数（`CLUSTER_YIELD` 调了三个值），
最后靠把断言从"比总数"改成"比格子的集合"才定位到。

**修法**：一次抽签 → 两段解读（先看是否成矿，再按累积概率定位矿种）。
互斥从此是**结构上的事实**，而不是靠运气。

### 缺陷 3：密度换算漏了 `−2`

矿只长在 `y ∈ [bottom+1, top−2]`，即每列 `thickness − 2` 层，
而**不是** `thickness` 层。同时 `per100` 的分母是**声明面积**，
可产矿格数却按**实际列数**算（轮廓侵蚀后两者不等，小岛相对差 3%）。

两处都漏掉时，晶矿岛煤实测 **2.16 格/100**，越出 PRD LOW 档的 `[1,2]`。

### 缺陷 4：种子对轮廓的影响过弱

只靠 `erode` 通道时，每格是否归属由 `d > 1 - erode` 决定，
而 `erode` 的值域被 `OUTLINE_MAX_EROSION` 压到 0.06 以内 ——
于是只有 `d ∈ (0.94, 1.0]` 这圈**极窄的环带**会随种子翻转。
实测两 seed 仅 **18 列**不同（判据要求 > 20）。

**修法**：增加第二个与 `d` 无关的 `jitter` 通道（纯 seed 决定），
让整条边缘都随 seed 变化；其量级仍受 `OUTLINE_MAX_EROSION` 约束，
所以尺寸误差不突破 2 格上限。

## 4. 夹具与产品分离（本轮的一条关键设计决定）

三个自测**仍然跑 `TestWorldGenerator`**。这不是偷懒，是它们各自的断言都钉在
**专门为它搭的平台上**：

| 自测 | 依赖的地形事实 |
|---|---|
| M1 | 虚空坑固定 `(3..6, 3..6)`、高台固定 3 格（"跳不上去"的对照组）、上行楼梯逐级 1 格、玻璃板固定跨 `x=0` 区块边界、出生点固定 `(0.5, 64.0, 0.5)` |
| M1.5 | 同上 + 背包/菜单的世界不动性 |
| M2 | 同上 + 怪物的贴地生成与近战几何 |

把产品世界换进去，这些断言会以「玩法没生效」的样子失败，
而真因是地形不同 —— 与 M2.2 那次「槽位口径」事故完全同族。

**判定口径**刻意**只看三个自测开关**，不看 `automated()`：
性能测量（`measureSeconds > 0`）**必须**跑产品世界，
否则测的是一块测试平台的数字，而 PRD 12.5 的性能门禁针对的是玩家实际会加载的世界。

可用 `-Dskyisland.generator=test|islands` 覆盖。

### 用覆盖开关做的诊断（`-Dskyisland.generator=islands` 跑 M1 自测）

**6 条失败，全部指向"地形不同"而非"玩法坏了"**：

```
FAIL 挖掘成功至少 1 个方块            （出生点在屋内，瞄准不到可挖格）
FAIL 脚下方块 (0,63,0) 变成空气        （该格是小屋地板，且在身下）
FAIL 放置成功至少 1 个方块
FAIL 射线目标指向脚下方块
FAIL 放置位置 (0,64,-7) 的方块 ID
FAIL 出生点站定在地板上（y 期望 64.0）
```

**最后一条已用物理探针澄清**：玩家在屋内 `onGround=false`，
跳 20 步后 `y=65.145`（内部净空 64–66，够跳），
朝南走 180 步走出到 `z=13.20`、`onGround=true` —— **门是通的，出生点可达**。
失败的真因是自测对出生点的假设（"站在裸地上、脚下是草"），不是产品缺陷。

## 5. ★ 登记的规格冲突（未擅自改引擎）

PRD 4.1 / 4.6 写「主岛基准面 **y = 64**（岛屿表面层）」，
而引擎自 M1 起冻结的是 `Coords.WORLD_SURFACE_BLOCK_Y = 63`（脚底 y = 64）。

**本轮服从引擎常量**。理由：改引擎常量会让 M1–M5 全部存档、三个自测、
出生点与资源核心 y 一起位移，代价远大于收益；而「表面层」的**物理含义**
（脚踩的那一层）在两套口径下是同一个高度。

岛屿厚度按 PRD「自表面层向下 8–14 层」执行：表面方块 y=63 时底部落在
y = 56（8 层）至 y = 50（14 层）。资源核心放在表面方块**之上**一格（y = 64），
与 `TestWorldGenerator` 的既有做法一致（核心 = 玩家站得到的位置）。

> 建议主理人裁决：是否回填 PRD §4.1 / §4.6 的 y 口径，
> 或在 §4.1 加一句"表面方块 y=63、脚底 y=64"的引擎裁定引用。
