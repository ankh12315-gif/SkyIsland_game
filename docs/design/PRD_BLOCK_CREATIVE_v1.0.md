### 3.3 必须新增的两个非方块物品

方块掉落**非方块物品**时，该物品必须真实注册，否则掉落会变成"凭空消失"：

| 物品 | 稳定 ID | 用途 | 来源 |
|------|---------|------|------|
| 金矿石（物品形态） | `skyisland:gold_ore` | 合成输入 | 金矿石方块掉落 |
| 小麦种 | `skyisland:wheat_seeds` | 种植小麦 | 小麦方块掉落（×1–2） |

> ★ **`ItemRegistry` 的方块物品与方块严格对齐**（方块物品排在物品表最前面）。
> 因此新增方块会**连带**新增同名方块物品，这是既有契约，不是新增负担。

### 3.4 方块数量口径（必须可断言，不得靠人工数表）

| 口径常量 | 值 | 说明 |
|---|---|---|
| `MVP_CORE_PLAYER_BLOCK_COUNT` | **13**（不变） | PRD 5.1 前 13 行，**不因本轮改变** |
| `ALPHA_ORE_BLOCK_COUNT` | 2（不变） | 铜矿石 + 晶体矿石 |
| `ALPHA_CONTENT_BLOCK_COUNT` | **3**（新增） | 金矿石 + 小麦 + 石砖 |
| `POST_MVP_BLOCK_COUNT` | **2**（新增） | 铁块 + 台阶 |
| `playerBlockCount()` | 20（本轮后） | 13 + 3 + 2 + 铜/晶体 2 |

> **13 这个数字不许动。** 它是"PRD 的 MVP 口径没被本轮改动"的唯一可断言证据。
> 若有人顺手把它改成 20，`BlockRegistryTest` 立刻变红 —— 这正是它的用途。

### 3.5 台阶的最小可玩形态（范围收敛，防范围蔓延）

台阶需要 block state，而 block state 会牵动网格、碰撞、放置判定、存档四层。
为避免一个装饰性方块拖垮整个里程碑，**本轮只做"下半形态"**：

| 项 | 本轮 | 明确不做 |
|---|---|---|
| 形态 | 仅 `slab`（下半） | 上半 `slab_top`、双台阶、角台阶 |
| 放置 | 放在实心方块**上半格**或地面 | 靠墙自动贴附 |
| 跳跃 | 可跳上（半高） | — |
| 存档 | 写 `skyisland:slab` | 写形态后缀 |

> **上限形态的移除条件**：当"木门开关"（MVP-BLOCK-016）落地、block state 机制已存在后，
> 再补 `slab_top`。本轮**不预先**造这个状态字段。

## 4. 创造模式：模式选择

### 4.1 新建世界流程

| 步骤 | 规格 |
|---|---|
| 入口 | 主菜单 → 新的世界 |
| 新增一步 | **模式选择：生存（默认） / 创造** |
| 默认值 | **生存**（缺省即生存，防止手滑进创造毁档） |
| 选择后 | 该模式的初始物资与规则**一次性**写入存档 |
| 切换 | **不支持中途切换**（见 §4.3）；**但允许「本次运行内的创造会话」，见 §4.3′** |

### 4.2 存档必须记录模式

| 规格项 | 定义 | 优先级 |
|--------|------|--------|
| 存档字段 | `gameMode = survival \| creative` | 【必须】 |
| 缺省行为 | 读取旧存档**没有**该字段时**按 survival 处理** | 【必须】 |
| 模式锁定 | 存档一旦创建，模式**不可改** | 【必须】 |
| 可读性 | 启动日志打印一行 `游戏模式 : 生存 / 创造` | 【必须】 |

> ★ **旧存档缺字段必须落到 survival（安全侧）**，与本项目既有惯例一致
> （`skyisland.infiniteReserve` / `skyisland.loadout` 都是"写错一律留在有限侧"）。
> 判据同样是：**漏配 / 写错值 / 旧存档，一律留在生存模式**。

### 4.3 为什么不支持中途切换（显式裁定）

允许切换会带来两个坏结果，且都不是"以后再说"能解决的：

1. **创造模式刷出的无限方块会留在世界里** —— 切回生存后，玩家面前是一堆本不该存在的建筑，
   而它们的产出无法回溯，生存平衡被永久污染。
2. **存档里没有任何字段能表达"这个方块是创造来的"** —— 要支持就得给每个方块位加来源标记，
   这是存档格式的破坏性变更。

**裁定：模式在存档创建时确定，永不切换。** 想玩创造就新建一个世界。

#### 4.3′ 修订（2026-10-08，主理人裁决）：允许**本次运行内**的创造会话

主理人要求「连按两下空格就开创造模式，直接可以起飞」。这与 §4.3 直接冲突，
而 §4.3 的两条理由**并未因此失效** —— 尤其第②条（存档没有"这个方块是创造来的"
标记，要真支持就是存档格式的破坏性变更）**无法绕过**。

⇒ 采用的折中：**会话只在本次运行内有效，不写入存档。**

| 规格项 | 定义 | 优先级 |
|--------|------|--------|
| 入口 | **双击空格**（窗口 0.3 秒，与 §5.4 飞行用同一个键） | 【必须】 |
| 效果 | 进入创造会话（§5.1–§5.5 五项能力全部生效）**并直接起飞** | 【必须】 |
| **不写存档** | 会话状态**不得**进入 `level.json`。`gameMode` 全程只由存档自身决定 | 【必须】 |
| 重启行为 | 退出游戏再进来，**自动回到生存** | 【必须】 |
| 三态循环 | ① 生存未开会话 → 进会话 + 起飞；② 已在创造里 → **只切飞行** | 【必须】 |
| **退出路径** | **不**由双击空格承担；走 ESC → 暂停菜单「结束创造模式」 | 【必须】 |
| 状态可见性 | HUD **常驻**显示「飞行中」或「创造会话中」，**不论是否站在地面** | 【必须】 |
| 创造存档 | 双击空格只切飞行；退出同样走 ESC 菜单 —— §4.3「模式不可切换」原样保留 | 【必须】 |
| 可见提示 | 进入与退出各弹一条，且必须写明「不写入存档」与「建筑仍然留在世界里」 | 【必须】 |

**为什么用同一个键走完三态，而不是"进创造"与"退创造"分两个键：**
退出路径若放在另一个**手感键**上，玩家会不知道它存在，于是被留在创造会话里；
而"被留在创造会话里"的后果不是"关不掉游戏"，而是**生存平衡被污染且无提示**。

> ★ **2026-10-09 修订**：本条在三态版本下**被主理人实测推翻**。
> 原设计让"第三次双击空格"承担退出，实测结果是：
> 按 Ctrl 下降到地面 → 第 1 次双击停飞 → **第 2 次退出创造、能力全没** → 第 3 次才重新起飞。
> 两个致命问题：
> ① **不可预测**：站在地面时 `flying` 仍可能是 true（悬停在地面上方），
>    而它与"没在飞"**看起来一模一样** ⇒ 同一个键在看起来一样的两种状态下
>    做完全不同的事，玩家无从预判。
> ② **不可逆**：触发它是一次手感键的连按，而后果是**静默拿走全部五项能力**。
>    一个键静默拿走你的全部能力，比它什么都不做更糟。
> ⇒ 双击空格现在**只**切飞行（Minecraft 语义）；退出走 **ESC → 暂停菜单**，
>   那是玩家预期找得到、且不会误触的地方。
> ⇒ 并强制要求 HUD **常驻**显示飞行/会话状态 ——
>   **不可见的状态就是不可预测的操作**。

**残留代价（知情接受）**：用无限方块盖的建筑**仍然留在世界里**。
在不改存档格式的前提下这一点无法消除（§4.3 理由①）。主理人 2026-10-08 已知情选择接受。

**实现与验收**：`Player#applyDoubleTapSpace`（三态的唯一落点）；
行为守卫 `CreativeSessionTest`；接线守卫 `CreativeSessionWiringTest`
（守"不得写盘 / 创造存档不得有退出路径 / 面板跟着会话重建"）；
反向验证 `tmp/rv_creative_session.js`（7 条断线）。

#### 4.3′′ 修订（同日晚）：**取消独立的创造入口**

主理人裁决「不要分成两个文件进入」。§4.3′ 落地后，「想玩创造」已经有了
游戏内的入口（双击空格），于是**独立入口失去了存在理由**，本轮删除：

| 被删项 | 位置 |
|---|---|
| 创造入口 .bat | `play-creative.bat` |
| 启动器的创造分支 | `skyisland_launcher.c` 的 `#ifdef SKYISLAND_CREATIVE`（及其 `SkyIsland-creative.exe`） |
| 该入口的同步守卫 | `tmp/check_creative_sync.js`（及其 `.gitignore` 白名单） |
| 桌面按钮 | 「SkyIsland 创造.exe」 |

**删的四条理由**（不是"少一个按钮"这么轻）：

1. **死代码**：留下 `#ifdef SKYISLAND_CREATIVE` 而没有第二个 exe，
   就是本项目明令禁止的「定义了却无消费者」。
2. **同一个键两套行为**：创造世界里双击空格**没有**退出路径（§4.3 保留），
   生存世界里才有（§4.3′ 新增）。两个入口玩同一个游戏，
   而同一个键在两个世界表现不同 —— 这本身就是坑。
3. **守卫会跟着烂掉**：`check_creative_sync.js` 守的就是"创造入口指向另一个世界"，
   文件删了它就变成一份对着不存在文件运行的脚本。
4. **主理人的明确要求。**

⇒ 现在**只有一个游玩入口**（桌面 exe / `play.bat`，指向同一个世界 `islands-play`），
由 `tmp/check_play_sync.js` 守住一致。
`NativeLauncherWiringTest#thereIsExactlyOnePlayEntryPoint` 是一条**禁止性**断言：
三样东西都不得复活。

## 5. 创造模式能力清单（主理人全选，五项全做）

### 5.1 方块面板（背包内无限）

|--------|------|

## 6. 方块贴图：程序化像素贴图

### 6.1 技术方案（与既有技术裁定一致）

`docs/architecture/technical-constraints.md` §3.4 早已裁定采用**纹理数组**，
本文只是把它从"技术债"变成"已实现"：

| 规格项 | 值 |
|--------|---|
| API | `GL_TEXTURE_2D_ARRAY` |
| 尺寸 | **16 × 16**，所有方块一致 |
| 层数 | **≥ 方块数**（20 玩家方块 × 1.0–1.2 倍；空气与 `resource_core` 不占层）。<br>美术 2026-10-05 实测：草方块 / 原木 / 木门 / 台阶需多张面贴图 ⇒ **共 24 层**。含 mipmap 约 32 KB。<br>（初稿写"= 方块数"与 §6.3 的三贴图规则**自相矛盾**，已按主理人裁决改为 ≥） |
| 来源 | **程序化生成**（不引入任何图片资源文件） |
| 过滤 | **最近邻**（保持像素锐利）+ **mipmap** |
| UV 策略 | **每面 UV = 该面在该层内的满幅区域**（0..1），不跨层取样 → 无渗色 |
| 层号传递 | 顶点属性携带 `layerIndex` |

### 6.2 顶点格式变更（**破坏性**，必须显式登记）

当前 `MeshData` **明文不含 UV / 纹理层号**：

```
offset  0 : position  vec3   (区块局部坐标 [0,16])
offset 12 : color     vec4   (顶点色 rgb + 预乘明暗 a)
stride = 28 字节（7 float）
```

**本轮变更**：

| offset | 字段 | 类型 | 说明 |
|--------|------|------|------|
| 0 | position | vec3 | 不变 |
| 12 | color | vec4 | **语义收窄**为"光照 × 贴图取样"（rgb 不再是方块本色） |
| **28** | **layer + ao** | **float2** | **新增**：`x` = 纹理层号，`y` = 环境光遮蔽 |

**新 stride = 36 字节（9 float）**。

> ★ **`color` 字段不能删。** 它承载**明暗**（面明暗 × 光照 × AO），
> 删掉会让方块失去立体感 —— 贴图是"表面图案"，明暗是"光照"，两者是**乘算**关系。
> 若只做贴图不做明暗，方块会看起来像一张平的贴纸。

> #### ★ 修订（2026-10-06 主理人复核后补记）：本节漏记了三个消费方
>
> 初稿只写了"同步登记三处"，**这是错的**。读 `Renderer.java:151-154` 可见
> **同一个 `voxelShader` 被四个渲染器共用**：
> ```java
> chunkRenderer.render(world, camera, voxelShader, frustum);
> entityRenderer.render(voxelShader, camera, entities);
> combatFxRenderer.render(voxelShader, camera, fx);
> crackOverlay.render(voxelShader, camera, player);   // ← 同样用 voxelShader
> ```
> 而它们**各自硬编码了自己的顶点布局**：
>
> | 消费方 | 硬编码位置 | 值 |
> |---|---|---|
> | `MeshData` | 第 31 行 | `FLOATS_PER_VERTEX = 7` |
> | `Boxes` | 第 43 行 | `FLOATS_PER_VERTEX = 7` |
> | `CrackOverlay` | 第 88 行 | `FLOATS_PER_VERTEX = 7` |
> | `CombatFxRenderer` | 第 49 行 | `FLOATS_PER_VERTEX = 7` |
> | `voxel.vert` | 第 20 行 | `layout (location = 1) in vec4 aColor;` |
>
> **不改齐的后果不是编译错，是画面静默损坏**：
> `aLayer` 读到的是别处的字节，实体 / 粒子 / 裂纹的几何会错乱或消失，
> 而**编译与全部单测依然全绿** —— 因为没有任何断言问过"四个渲染器的 stride 是否一致"。
>
> ⇒ **本轮的硬要求**：stride 必须收敛为**单一真相源**（一个常量），
> 四个渲染器一律引用它，不得各自写死；并补一条断言把"四者一致"钉死。
> 这与本项目反复吃过的"脆绿灯"是同一类，必须在改之前就建好守卫。

### 6.3 六面 UV 规则

同一种方块的**六个面通常用不同贴图**（草方块顶面是草、侧面是草边、底面是泥土）。
本轮采用**三贴图一组**的简化规则（与《我的世界》的 grass block 同构）：

| 面的类别 | 贴图层 | 适用方块举例 |
|---|---|---|
| 顶面 | `*_top` | 草方块（草）、沙（沙） |
| 侧面 | `*_side` | 草方块（草边）、原木（木皮） |
| 底面 / 其余面 | `*_top`（复用）或纯色 | 草方块底面用泥土层 |

> **纯色方块只占一层**（如玻璃、铁块用程序化纯色 + 描边），六个面共用。
> 规则由 `BlockTextures` 单点定义，网格器只读，**不许在网格器里 if/else 判方块名**。

### 6.4 程序化生成的硬约束

| 约束 | 理由 |
|---|---|
| **不引入任何外部图片文件** | 项目至今零资源依赖，不为一个功能破坏构建链 |
| 生成结果**确定性** | 同一方块每次生成必须逐像素一致，否则 mipmap 与截图取证会抖动 |
| 每张贴图生成后**自检**：非纯色像素占比 > 0 | 防止"忘了画"生成出纯色贴图却在屏幕上看起来正常 |
| 16×16 全部落在 `[0,1]` 归一化 UV 内 | 防止采样越界导致相邻层渗色 |

### 6.5 性能约束（继承 M1 门禁，不放松）

| 规格项 | 值 |
|--------|---|
| 目标 | 视距 6 区块 + 集成显卡 **60 FPS**（M1 门禁硬约束，不得放松） |
| 新增成本 | 纹理数组常驻显存：20 层 × 16×16 × RGBA + mipmap ≈ **数十 KB 量级** |
| 风险 | 额外一次纹理采样（`sampler2DArray`）可能使填充率成为瓶颈 |
| 门禁 | 必须重跑 `perf_gate_met`，与 M1 基线对比**不得显著劣化** |

> ★ **若采样导致 60 FPS 不达标，第一顺位对策是"降低生成开销"，不是"放弃贴图"。**
> 不得以"性能不达标"为由静默退回纯色 —— 那会让本轮"加贴图"的裁决悄悄失效。
> 若确需退回，必须**回到主理人**重新裁定。

## 8. 实施顺序建议（每步都必须跑测试，前一步失败不得堆后续）

> 本节是**建议**，不是已批准的实施计划。**未经主理人确认不得开工。**

| 步骤 | 内容 | 完成判据 |
|---|---|---|
| S1 | **异形网格与碰撞支持**（R1） | 小麦 / 台阶 的碰撞体为空、网格为十字面；有单测 |
| S2 | **顶点格式扩展**（R2） | stride 36；`MeshData` 与着色器测试同步通过；画面与改动前一致（纯色回退） |
| S3 | **纹理数组接入 + 片元着色器改采样贴图 alpha** | 一张纯色贴图先跑通全链路；截图取证；**玻璃边框不透明 + 内部半透**、树叶镂空可见 |

> ★ **主理人 2026-10-06 裁决：片元着色器的透明改造并入 S3，不许留到 S4。**
> 依据（美术提出、主理人复核成立）：现有 `voxel.frag` 是
> `fragColor = vec4(vColor.rgb * vColor.a, uAlpha)`，而 `uAlpha` 是**单一 uniform**
> （不透明 1.0 / 透明 pass 一个常数）。不改造则：
> 玻璃做不到"边框不透明 + 内部半透"（变成实心浅蓝砖），
> 树叶与小麦的镂空像素会被画成半透明方块 —— **这两项直接作废**，
> 且拖到 S4 必然返工。改法：`fragColor = vec4(texel.rgb * light, texel.a * uAlpha)`。

> ★ **铁律（美术提出、主理人复核成立）：贴图一律 albedo-only，不烘方向光。**
> `BlockFace.shade()` 已给面明暗（顶 1.00 / ±Z 0.85 / ±X 0.65 / 底 0.50），
> 贴图再画一次受光边会把顶面打爆、底面压死。
| S4 | **20 种方块的贴图生成** | 每张非纯色；像素级单测 |
| S5 | **补 5 种方块**（§3） | `BlockRegistryTest` 同步；`RecipeRegistry.verify()` 通过 |
| S6 | **模式存档字段**（§4.2） | 旧存档缺字段落 survival；有单测 |
| S7 | **创造面板**（§5.1） | 面板**不含资源核心**；有断言 |
| S8 | **创造五项能力**（§5.2–§5.5） | 每项一条断言 + 真人试玩 |
| S9 | **性能复测** | `perf_gate_met` 与 M1 基线对比 |

> ★ **S2 有一个必须先验证的前提**：改顶点格式后**画面应当与改动前一致**
> （此时纹理数组尚未接入，或接入了纯色层）。
> 若这一步画面就变了，说明改坏了 —— 这是一个**免费的回归检测点**，不要跳过。
