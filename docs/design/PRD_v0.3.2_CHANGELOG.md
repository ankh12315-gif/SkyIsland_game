## 0. 本轮的性质与边界（先读）

1. **本轮是"决策闭合"，不是"需求扩张"。** v0.3.2 相对 v0.3.1 的全部改动，都是把用户已拍板的 11 项冲突写回 PRD；**不新增任何玩法、不新增任何数值、不改变任何里程碑定义**。
2. **采用点修（Edit）而非重写。** v0.3.1 的章节骨架、表格结构、全部既有数值原样保留；改动仅在必要单元格与新增行上。
3. **PRD_v0.3.1.md 全程未被修改。** 如需追溯旧口径，请查 v0.3.1 原文。
4. **Requirement ID 一律沿用 324 条体系。** 本轮**没有**新建 ID；若某项裁决在 324 条清单中**找不到**对应条目（因为 v0.3.1 把它标成了【后续迭代】或【Alpha 必须】），本文在"受影响 Requirement ID"段中**明确写"无现有 ID"**并给出建议新增编号，**不擅自编造已完成登记的事实**。
5. **本轮不写技术实现。** 字体渲染、粒子后端等技术方案一律不进 PRD；技术侧裁决只在本文 §3 以"技术侧伴随裁决（不写入 PRD）"形式记录。

### A1 — 破坏特效（8–12 个方块颜色粒子）口径锚定

**旧口径（v0.3.1）**
§5.2 行 413 写「破坏特效：破坏瞬间生成 **8–12 个方块颜色粒子**（Alpha 起补全规格），播放破坏音效」，标【MVP 必须】（占位）／【Alpha 必须】（完整）。未写明 MVP 到底在哪个里程碑交付。技术侧 `TECH_DESIGN_v0.1` §H.4 / §M.7 把它写成"**3–5 个**"粒子，形成静默降级（登记为 DRIFT-A-01）。M1 / M1.5 实际只做了 10 段裂纹视觉（CrackOverlay），粒子与音效均缺失（技术债 T-8.9）。

**新口径（v0.3.2）**
§5.2 行 417 改为：

> 「破坏特效（v0.3.2 锚定）：破坏瞬间生成 **8–12 个方块颜色粒子**（MVP 占位规格），播放破坏音效（MVP 占位音）。**实现时点：M2 建立粒子后端时交付最小 8–12 个方块色粒子**；Alpha 再做正式粒子表现」——优先级【MVP 必须】（占位，M2 交付）／【Alpha 必须】（完整）。

即：**数量维持 8–12 不变**，新增了**唯一可验收的交付时点（M2）**，并明确 Alpha 只做"正式表现"而非"从无到有"。

**裁决原因**
1. **PRD 是产品口径，技术文档的降级不构成对 PRD 的修改。** "3–5 个"是技术侧在实现困难下自行缩水的结果，未经产品裁决，属静默降级；若承认它，等于允许实现反向改写需求，后续所有数值都失去约束力。
2. **缺的不是"要不要做"，而是"什么时候做"。** v0.3.1 只写"MVP 占位"，M1 可解释为"占位即暂不实现"，M2 可解释为"占位即简化实现"——这正是它拖到人工试玩才暴露的根因。锚定 M2 后，M2 门禁即可直接卡这一条。
3. **粒子后端本身在 M2 才存在**，M1 无粒子系统，要求 M1 交付不具可行性；把 MVP 占位锚在 M2 是"可实现 + 可验收"的唯一交点。

**受影响 Requirement ID**
- `MVP-MINE-007` —— 「破坏瞬间生成 8–12 个方块颜色粒子」（原阶段判定 M1，**应随本裁决改为 M2**）。
- `MVP-MINE-008` —— 「播放破坏音效」（与 MINE-007 同源于 v0.3.1 行 413，措辞随本行改写；破坏音效亦属 T-8.9，同一交付时点）。

> **DRIFT 状态变更**：DRIFT-A-01 从"PRD 与技术文档冲突、待裁决"变为"**PRD 已锚定，技术文档待跟随修订**"。`TECH_DESIGN_v0.1` §H.4 / §M.7 的"3–5 个"**仍是错的**，需 engineering-lead 按 v0.3.2 改为 8–12。

### A2 — 手枪合成归 Alpha（手枪为开局装备，MVP 不可合成）

**旧口径（v0.3.1）**
三处互相打架：
- §5.4.1 行 494：手枪行「合成材料 = 铁锭 ×4 + 火药 ×2 + 木板 ×2」，优先级【MVP 必须】；
- §5.6.2 R14（行 668）：手枪配方标【**Alpha 必须**】；
- §2.2 / §5.7：手枪是**开局赠送装备**（初始物资含手枪 ×1）。

即：MVP 既要"开局送你一把枪"，又要"MVP 必须能合成这把枪"，而合成表又说它是 Alpha。登记为 DRIFT-C-01。

**新口径（v0.3.2）**
- §5.4.1 行 498：合成材料列改为「**—（MVP 不可合成）**；手枪为**开局装备**，其合成配方（R14：铁锭 ×4 + 火药 ×2 + 木板 ×2）归**【Alpha 必须】**」；优先级拆为「【MVP 必须】（枪械本体）／【Alpha 必须】（R14 合成配方）」。
- §5.4 设计说明行 538：重写为「手枪**开局获得**（MVP，MVP 内**不可合成**）……**MVP 的枪械 progression 重点是持续弹药供应，而非重新制造初始手枪。**」
- §5.6 行 709：结论段「接近手枪合成门槛」→「接近**弹药合成（R11）**门槛」，并加注「MVP 内不存在"手枪合成门槛"」。
- §5.7 行 736：铁锭 ×4 用途改为「接近**弹药合成（R11）门槛**……手枪合成配方 R14 归 Alpha（见 5.4.1），MVP 不以此作为手枪门槛」。
- §9.2 行 935：MVP 内容清单枪械行改为「**只做手枪**（**开局装备，MVP 不可合成**）……其余 3 把枪与**手枪合成配方 R14** → Alpha」。

**裁决原因**
1. **枪械本体与枪械配方是两件事，v0.3.1 把它们塞进同一行同一优先级，是矛盾的直接来源。** 拆开后"MVP 有枪"与"Alpha 才有配方"不再互斥。
2. **开局赠送手枪是 P2 支柱（首夜可自卫）的承载物，不能动**；可动的是"MVP 是否还要再造一把"——答案是否定的，因为 MVP 只做 1 把枪，重造一把没有玩法收益，只会稀释"远征 → 弹药"这条唯一的 progression 线。
3. ** progression 主线守恒**：初始铁锭 ×4 的设计意图（早期目标引导）原本挂在"接近手枪合成门槛"上，手枪合成归 Alpha 后该意图会落空；改为挂到 **R11 弹药合成**上，意图不丢失，且 MVP 合成配方仍为 7 条（R14 本就不在 7 条内），数量口径不变。

**受影响 Requirement ID**
- `MVP-COMBAT-006` —— 「合成材料 铁锭 ×4 + 火药 ×2 + 木板 ×2」。**该条应标记为：MVP 范围内作废，降级为 Alpha（R14）**；quality-lead 的追踪矩阵需改口径，否则会误判 M2 缺一个合成配方。
- `MVP-SCOPE-005` —— 「合成配方 MVP 7 条」（口径未变，本裁决确认 R14 不在 7 条内，无需改动但需复核）。
- `MVP-SCOPE-002` —— 「枪械 MVP 1 种」（口径未变，作为本裁决的范围护栏）。
- §9.2 行 935 的枪械行**在 324 条清单中无专属 ID**（清单对 §9.2 只登记了 SURV-019/020/021 三条玩家行）。本处改动为口径一致性改写，不改 Requirement 语义，建议 quality-lead 在矩阵中作为 `MVP-SCOPE-002` 的交叉引用处理。

### A3 — 换弹（Reload）统一规则

**旧口径（v0.3.1）**
§5.4.3 行 520–521 分散写着：
- 「换弹条件：弹匣未满且有对应弹药；换弹期间不可开枪，可被移动打断」；
- 「满弹匣换弹：允许，弹出剩余弹药不损失（回背包）」。

三个未定义处：① 后备弹药**不足**时能不能换、装多少（DRIFT-A-06）；② "被移动打断"是**暂停**还是**取消**、被打断时弹药归属谁；③ "满弹匣换弹允许"与"弹匣未满才可换弹"**自相矛盾**。

**新口径（v0.3.2）**
§5.4.3 行 524–526 改为三行：

| 行 | 内容 |
|----|------|
| 524 | **换弹条件（统一规则）**：① 弹匣**已满** → 按 R **无操作**；② 弹匣未满且后备弹药 > 0 → **允许换弹**；③ 后备弹药不足 → **允许部分填充**，装载量 `load = min(弹匣容量 − 弹匣内弹药, 后备弹药)`，换弹完成时执行 `弹匣内弹药 += load` 与 `后备弹药 -= load`；④ 换弹**完成前不得提前转移弹药** |
| 525 | **换弹打断（新增）**：移动打断换弹 = **取消换弹**：`弹匣内弹药` 与 `后备弹药` 回到换弹开始前的状态；换弹期间不得开枪 |
| 526 | **满弹匣换弹（废止）**：**不允许**。v0.3.1 的「满弹匣换弹允许、弹出剩余弹药不损失（回背包）」口径**作废**；满弹匣时按 R 无操作 |

**裁决原因**
1. **"满弹匣换弹"本身就是无意义操作**：满弹匣时换弹不增加战斗力，唯一的实际效果是"触发一次 1.2 秒硬直"。留着它只会给玩家一个负收益操作，且需要一个"弹出弹药回背包"的特例逻辑去兜底——该特例是纯复杂度，无玩法价值。
2. **部分填充必须写死公式**：不写 `load = min(...)`，实现方只能自由发挥（要么拒绝换弹导致弹药锁死，要么清后备弹药导致资源蒸发）。两者都是玩家可感知的 Bug，且都会在人工试玩才暴露——与本次审计要根治的缺陷同类。
3. **打断语义必须是"取消"而非"暂停"**：若为"暂停"，会出现"打断后重新按 R 从中断处续上"的隐状态，玩家无法从 UI 判断当前进度；"取消 + 状态回滚"是唯一无隐状态、可断言的方案。
4. **"完成前不得提前转移弹药"** 是为了堵住"打断瞬间弹药既在弹匣又在后备"的复制漏洞。

**受影响 Requirement ID**
- `MVP-COMBAT-018` —— 「换弹条件：弹匣未满且有对应弹药」（口径被 524 行细化，须按新四则重写验收点）。
- `MVP-COMBAT-019` —— 「换弹期间不可开枪」（保留，并入 525 行）。
- `MVP-COMBAT-020` —— 「换弹可被移动打断」（语义变更：**打断 = 取消**，须重写验收点）。
- `MVP-COMBAT-021` —— 「满弹匣换弹允许，弹出剩余弹药不损失（回背包）」。**该条应标记为：口径已废止**；其 DRIFT-A-06（后备弹药不足时的行为未定义）**随之闭合**。
- `MVP-COMBAT-017` / `MVP-GATE-008` —— 换弹耗时 1.2 秒 ±0.1 秒（数值未变，不受影响，仅作回归确认）。
- **新增语义**：「部分填充公式 `load = min(弹匣容量 − 弹匣内弹药, 后备弹药)`」在 324 条清单中**无现有 ID**（v0.3.1 未定义该行为，故不可能被登记）。建议 quality-lead 新增 `MVP-COMBAT-031`。

### A4 — 快捷栏槽位切换（§5.4.3 口径统一为 1–9 + 滚轮）

**旧口径（v0.3.1）**
§5.4.3 行 527：「**枪械切换**：数字键 **1–4** 切换快捷栏对应槽位的枪械」，【MVP 必须】。与 §6.1 行 746「快捷栏 9 格，数字键 **1–9** 高亮当前槽」直接冲突（DRIFT-A-04）。技术侧 `TECH_DESIGN_v0.1` §I.7 已自行裁定为 1–9。

**新口径（v0.3.2）**
§5.4.3 行 532 改名并改为：

> 「**快捷栏槽位切换**（v0.3.2 改名并统一）：**数字键 1–9** 选择快捷栏对应槽位（**含非枪械物品**）；**鼠标滚轮**循环切换。**全文废止一切「仅 1–4」的描述**」——【MVP 必须】。

**裁决原因**
1. **快捷栏是 9 格（§5.6.1 / §6.1 / §6.2 三处同口径），键位却只覆盖 4 格，是纯矛盾，没有设计理由支撑。** MVP 唯一枪械只有 1 把，"1–4"可能是从"4 把枪（Alpha）"误抄过来的——Alpha 的枪械数被错当成了 MVP 的槽位数。
2. **"枪械切换"这个命名本身就是错的**：该键位切换的是**快捷栏槽位**，槽位里可能是方块、火把、弹药，不一定是枪。命名错误会导致实现只处理枪械、非枪械槽位按 1–9 无响应，形成"为什么按 5 没反应"的隐性缺陷。
3. **明确"含非枪械物品"**，是为了让实现不能只绑定枪械槽。

**受影响 Requirement ID**

### A5 — HUD 当前枪械名（简体中文显示名 + 内部 ID 分离）

**旧口径（v0.3.1）**
§6.1 行 748：「当前枪械名：屏幕右下角，弹药计数上方」，未写明显示什么语言、显示名从哪来。中文显示名与现有 `BitmapFont`（仅覆盖 ASCII 32–126）之间是不可兑现的缺口（DRIFT-B-04 / 技术侧"四重缺口"的一部分）。

**新口径（v0.3.2）**
§6.1 行 753 改为：

> 「当前枪械名：屏幕右下角，弹药计数上方，显示手持枪械的**简体中文显示名**（MVP 唯一枪械显示为「手枪」）。**玩家可见语言与内部 ID 必须分离**：显示名走 zh-CN 文案来源，内部 stable ID / Java 类名 / JSON key 仍用英文（如 `skyisland:pistol`）」

**裁决原因**
1. **"显示名"与"内部 ID"混用是本地化不可挽回的结构性错误**：一旦中文字符串进了 Java 代码或 JSON key，后续任何语言都加不进去，且存档 ID 会污染。在只有 1 把枪、1 种语言时分离成本最低，现在不做，M4 做代价极高。
2. **明确"MVP 唯一枪械显示为「手枪」"**，是把"显示什么"钉死成可断言的一条，而不是留给实现去猜显示 `pistol` 还是 `skyisland:pistol`。
3. **语言侧不再回避字模问题**——见 A8 的硬约束：展示能力不足是技术缺口，不是改产品规格的理由。

**受影响 Requirement ID**
- `MVP-HUD-008` —— 「当前枪械名：屏幕右下角，弹药计数上方，右下角显示手持枪械中文名」。口径扩充为"简体中文显示名 + ID 分离"，需重写验收点。
- `MVP-TEXT-002` —— 「术语统一」（与 A9 联动，作为术语与显示名的共同护栏）。

### A8 — 中文文案：语气口径 + 语言硬约束（不得因字模把规格降级为英文）

**旧口径（v0.3.1）**
- §6.7 行 836：「语气：简洁、克制、**口语化**；不使用感叹号与卖萌语气」。
- 全文无语言硬约束段。中文界面与 ASCII-only 字模的冲突只在审计备注里，PRD 未表态。

**新口径（v0.3.2）**
- §6.7 行 842：「语气（v0.3.2 修订）：简洁、克制、**直接、统一**；不使用感叹号与卖萌语气」。
- §6.7 行 853–856 **新增**语言口径硬约束段：

> 「**语言口径（v0.3.2 裁决，硬约束）**：玩家可见界面文字使用**简体中文**。
> **不得因为当前字体渲染能力（如现有 `BitmapFont` 仅覆盖 ASCII）而把产品规格降级为英文。**
> 展示能力不足属技术实现缺口，由技术侧以"建立 CJK-capable 字体渲染"方式解决，**不是改产品规格的理由**。
> 内部标识（stable ID / Java 类名 / JSON key）一律保持英文，与玩家可见语言严格分离。」

**裁决原因**
1. **"口语化"与"不使用感叹号与卖萌语气"本身打架**：口语化的自然结果是语气词与感叹号。改"直接、统一"后两条要求不再互斥，且"统一"为 A9 的术语/Display Name 提供同一把尺子。
2. **最关键的一条：截断"实现能力反向改写产品需求"的通路。** 如果只是因为字模不支持中文就把界面改成英文，那么产品文档将不再是需求基线，而是"当前能做什么"的记录本——本次审计暴露的 T-8.9（破坏反馈缺音效与粒子）正是同一条通路上的产物。本条是对**这类缺陷的根因**下的裁决，不只是改一行文案。
3. **区分"产品口径"与"技术方案"**：PRD 只规定"必须是中文"，不规定"用什么字体渲染"；后者留给技术侧（见 §3）。PRD 写技术选型会造成文档耦合与双重维护。

**受影响 Requirement ID**
- `MVP-TEXT-001` —— 「语气：简洁、克制、口语化」（**"口语化"须改为"直接、统一"**）。
- 语言硬约束在 324 条清单中**无现有单一 ID**（v0.3.1 无此段，故不可能被登记）。它是对 `MVP-TEXT-001`–`012` 整组与 `MVP-HUD-008`、`MVP-SET-008` 的**上位约束**。建议 quality-lead 新增 `MVP-TEXT-013`（玩家可见界面文字为简体中文，且不得因渲染能力降级为英文）。
- `MVP-SET-008` —— 随 A6 作废设置项维度，但语言语义由本条承接（**语义不丢失**）。

### A9 — 术语统一 + Display Name 数据来源（localization lookup）

**旧口径（v0.3.1）**
§6.7 行 837：「术语统一：全游戏统一使用：方块、枪械、弹药、饥饿、生命、虚空、资源岛、资源核心；不改用同义词。」——只规定了"用哪些词"，没规定"这些词存在哪里、代码从哪取"。

**新口径（v0.3.2）**
§6.7 行 843 扩充为：

> 「术语统一与 Display Name 来源（v0.3.2 扩充）：……**玩家可见名称必须有统一的 Display Name 数据来源（localization lookup）**，示例：`pistol → 手枪`、`pistol_ammo → 手枪弹`、`iron_ore → 铁矿石`、`coal → 煤炭`；**内部 stable ID 保持英文**；**禁止在 Java UI 代码里散落中文字符串字面量**。为后续本地化保留 `displayName key / localization lookup` 结构，**本轮只实现 zh-CN**」

**裁决原因**
1. **"统一用词"如果只写在文档里，约束力为零。** 只有落到"数据从哪来"（lookup）与"禁止什么"（代码里不得出现中文字面量），才可能被 code review 与测试断言捕获。
2. **给出四组示例映射**，把 `MVP-HUD-008` 要求的中文枪械名、合成页的缺料提示（`MVP-TEXT-012`：「缺少 铁锭 ×4」）等一次性钉到同一张表上，避免各 UI 各自硬编码、彼此不一致。
3. **"本轮只实现 zh-CN"** 是范围护栏：建立结构 ≠ 建立多语言，防止 A6/A8 的裁决被读成"MVP 要做多语言"。

**受影响 Requirement ID**
- `MVP-TEXT-002` —— 「术语统一」（扩充为含 Display Name 来源，须重写验收点）。
- `MVP-HUD-008` —— 「右下角显示手持枪械中文名」（Display Name 的第一个消费者，与 A5 联动）。
- `MVP-TEXT-012` —— 「合成缺料显示『缺少 铁锭 ×4』」（需用 lookup 取"铁锭"显示名，不得硬编码）。
- `MVP-TEXT-003` / `004` / `005` / `009` / `010` —— 均为玩家可见文案，受同一 lookup 约束（**语义不变，仅增加取值来源要求**）。

### A10 — 石砖 `skyisland:stone_brick` 归 Alpha，且不得进入 MVP Block Registry

**旧口径（v0.3.1）**
§5.1 行 389：「石砖：v0.2 标为首版必须但未列入方块表，本版与 R18 一并移入【Alpha 必须】。」——只说了优先级，未约束"Registry 里到底注不注册它"。实操中很容易出现"顺手先注册上，反正玩家拿不到"的做法，导致 MVP 方块数口径（13 + 1）被悄悄突破，且存档里出现一个 MVP 不该有的 ID。

**新口径（v0.3.2）**
§5.1 行 393 **新增**硬约束：

> 「**石砖（v0.3.2 裁决，硬约束）**：稳定 ID 为 `skyisland:stone_brick`（**单数**），归**【Alpha 必须】**。**MVP 的 Block Registry bootstrap 不得登记它**（含任何拼写变体，如 `stone_bricks`）；**不得以"玩家暂时无法获得"为由让 Alpha 内容继续留在 MVP Registry 中**。M4 再正式重新登记。」

**裁决原因**
1. **"优先级归 Alpha"与"代码里存在"是两件事。** 只写前者，实现方可以合理地认为"先注册、不开放获取"也是符合 Alpha 归属的——结果是 MVP 的方块 Registry 含 Alpha 内容，数量口径、存档 ID 集合、§9.4 负面清单同时失真。
2. **ID 拼写必须钉死（单数 `stone_brick`）**：`stone_brick` / `stone_bricks` 两种写法会导致 MVP 与 Alpha 的存档不兼容，而存档按稳定字符串 ID 落盘（§5.1.1），一旦落地就是不可逆的兼容债。
3. **"不得以玩家暂时无法获得为由"** 直接封死了最常见的绕过话术——这正是"未实现且未登记"类缺陷的变体：**已实现但登记为未实现**。
4. **给 M4 留了明确的回归动作**（重新登记），不是永久禁止。

**受影响 Requirement ID**
- `MVP-SCOPE-007` —— 「MVP 明确不实现：……石砖」负面清单。本条是其**可执行化**：不实现 = Registry 里也不得存在。
- `MVP-SCOPE-001` —— 「方块类型 MVP 13 种玩家常规 ＋ 1 种系统方块」（数量护栏，防止石砖成为"第 14 种玩家方块"）。
- `MVP-BLOCK-017` —— 「MVP = 13 种玩家常规方块 ＋ 1 种系统方块；系统方块单独计数」（同上）。
- `MVP-BLOCK-025` —— 「读取旧存档时若遇到未知 ID 必须有明确降级行为」（石砖不在 MVP Registry 时，若读到含它的存档须走降级路径）。
- 石砖本身**在 324 条清单中无 ID**（v0.3.1 即归 Alpha，不在 MVP 清单内），本条为**负面约束**，不新增 Requirement。

### A11 — 按键自定义（Key Rebinding）升至【MVP 必须】

**旧口径（v0.3.1）**
§6.5 行 812：「**按键自定义**：全部键位可改」，优先级【**后续迭代**】。而 M1.5 已交付完整键位重绑（M15-SPEC-10 / 11），17 阶段 UI 自测 59 条断言通过。文档写"以后做"，代码已做完——登记为 DRIFT-C-02。

**新口径（v0.3.2）**
§6.5 行 816：「**按键自定义（v0.3.2 提升）**：全部键位可改 | 见 6.6 | **【MVP 必须】**（原【后续迭代】，v0.3.2 提升；**M1.5 已交付并验收，不得删除现有实现**）」

**裁决原因**
1. **属"范围前移"，不是"缺口"。** 实现已完成并验收，把它留在【后续迭代】只会造成两伤：要么测试矩阵按"不该有"判它通过（漏测），要么将来有人按 PRD"清理"掉这段已验收代码（返工）。
2. **"不得删除现有实现"是显式护栏**：防止后续按 PRD 做范围裁剪时误删 M1.5 成果。这类"文档说没有、代码里有"的错位，与本次审计的起因病（文档说有、代码里没有）是同一枚硬币的两面。
3. **不扩需求**：本条只是把既有实现登记为 MVP，未增加任何新键位、新界面或新行为。

**受影响 Requirement ID**
- **324 条清单中无现有 ID** —— 因为 v0.3.1 把它标为【后续迭代】，按清单编制规则（只登记【MVP 必须】）本就不该入册，故确实没有 ID。

- **DRIFT-C-02 状态变更**：由"范围前移，待裁决"变为"**已裁决，PRD 已跟随**"，可关闭。

### R1.2 口径变化

- **旧（v0.3.2 行 525）**：移动打断换弹 = **取消换弹**；弹匣与后备回到换弹开始前的状态。
- **新（v0.3.2-r1 行 525）**：**移动不打断换弹** —— 按 R 之后可继续行走 / 跳跃 / 转向，1.2 秒走满即完成；弹药仍**只在完成这一刻转移**（规则④）；**换弹期间不得开枪**不变。
- **废止理由**：玩家无法从界面区分"被移动取消了换弹"与"换弹还没走完"（两者在 UI 上都是"没换完"），这条规则因此不可读；且它把换弹从一条时间线变成了带隐藏失败态的流程。规则④的存在意义本就是让"取消"零回滚成本 —— 取消口废止后它退化为更简单的不变量，无需改。
