### 1.2 LWJGL 版本选型

LWJGL 近期版本时间线（截至 2026-09）：

| 版本 | 发布日期 | 说明 |
|------|----------|------|
| 3.4.3 | 2026-08-23 | 最新，发布仅数周，**不采用**（避免尝鲜） |
| **3.4.2** | **2026-07-13** | **【结论】采用**，已有两个月以上实战检验 |
| 3.4.1 | 2026-02-04 | 备选（更稳但偏旧） |
| 3.4.0 | 2026-01-18 | 引入 FFM API 支持（需 JDK 25 才可走 `--sun-misc-unsafe-memory-access=deny`） |
| 3.3.6 | 2025-01-05 | 旧稳定线；早于 JDK 24/25，在更高 JDK 上可能出现 JNI 版本告警 |
| 3.3.3 | 2023-09-16 | 过旧，不建议 |

**【结论】** 采用 **LWJGL 3.4.2**。理由：

1. 3.4.x 发布于 JDK 23/24/25 之后，已知这些 JDK 的 JNI 版本，规避 `[ThreadLocalUtil] Unsupported JNI version detected` 这类「库早于 JDK」的告警。
2. **JDK 25 已是本项目目标**（PRD 12.6）；3.4.x 具备 FFM 通道，可配合 `--sun-misc-unsafe-memory-access` 参数控制 Unsafe 告警，与 JDK 25 口径兼容（见 1.5）。
3. 3.4.2 已有两个月以上实战检验，且发布于本项目 M0 之前，属稳妥选择。

**知识缺口**：LWJGL 3.4.x 的**最低 Java 版本**未逐版核实（3.3.6 官方为 Java 8+）。本项目使用 JDK 25，远高于任何可能的最低门槛，故不影响决策；若需在更低 JDK 上构建，须回查官方 Release Notes。

### 1.4 Maven 下 natives 的正确引入方式

**结论**：natives 通过**同一 artifact 的平台 classifier** 引入，`scope=runtime`，**不手工解压**。

机制说明：每个 LWJGL 模块有「Java 绑定 jar」与「natives jar」两份构件，natives jar 内部以 `windows/x64/...dll` 形式打包原生库。LWJGL 在运行期**自动从 classpath 提取 natives 到临时目录并加载**，无需配置 `java.library.path`，也无需在 pom 中做任何解压脚本。这是 **【结论】首选方案**。

参考 `pom.xml` 骨架（节选，完整骨架见附录 A）：

```xml
<properties>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  <maven.compiler.release>21</maven.compiler.release>
  <lwjgl.version>3.4.2</lwjgl.version>
  <joml.version>1.10.8</joml.version>
  <!-- Windows 优先；未来跨平台由 profile 覆盖此属性 -->
  <lwjgl.natives>natives-windows</lwjgl.natives>
</properties>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.lwjgl</groupId>
      <artifactId>lwjgl-bom</artifactId>
      <version>${lwjgl.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <!-- 1) Java 绑定（编译期 + 运行期都需要） -->
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl</artifactId></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-glfw</artifactId></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-opengl</artifactId></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-stb</artifactId></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-openal</artifactId></dependency>
  <dependency><groupId>org.joml</groupId><artifactId>joml</artifactId><version>${joml.version}</version></dependency>

  <!-- 2) 平台 natives：同 artifactId，带 classifier，scope=runtime -->
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl</artifactId>
    <classifier>${lwjgl.natives}</classifier><scope>runtime</scope></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-glfw</artifactId>
    <classifier>${lwjgl.natives}</classifier><scope>runtime</scope></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-opengl</artifactId>
    <classifier>${lwjgl.natives}</classifier><scope>runtime</scope></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-stb</artifactId>
    <classifier>${lwjgl.natives}</classifier><scope>runtime</scope></dependency>
  <dependency><groupId>org.lwjgl</groupId><artifactId>lwjgl-openal</artifactId>
    <classifier>${lwjgl.natives}</classifier><scope>runtime</scope></dependency>
</dependencies>
```

Future-proofing（可选，不阻塞首版）：用一个 profile 组按 OS/架构自动切换 `lwjgl.natives`（`natives-windows` / `natives-windows-x86` / `natives-linux` / `natives-macos`），激活条件为 `<os><family>` + `<arch>`。首版 Windows 优先，直接硬编码 `natives-windows` 即可。

**运行时 natives 解压**：LWJGL 默认提取到 `java.io.tmpdir` 下的隐藏目录。如遇企业环境对临时目录的写限制，可用系统属性指定目录：

```
-Dorg.lwjgl.system.SharedLibraryExtractDirectory=skysisland-natives
```

**结论**：不采用「手工解压 natives 到 `lib/` 并配 `java.library.path`」的方案；仅在打包为安装器时才需要该模式（首版不需要）。

### 1.5 JDK 25 LTS 兼容性说明（v0.3 更新）

> **口径变更**：PRD v0.3 第 12.6 节把目标运行/构建 JDK 从 **JDK 23 改为 JDK 25 LTS**。本节据此重判 LWJGL 在 JDK 25 下的可用性。**v0.2 的结论「JDK 23 是 LWJGL 最后零告警版本」在 JDK 25 口径下已不再适用，现予修订**；该结论仅在「以 JDK 23 为运行基线的旧口径」下成立。凡 v0.2 中「禁止升到 24+ / 26+」的表述一并废止。

| 议题 | 事实 | 对本项目的影响 |
|------|------|----------------|
| LWJGL 的 JNI 本质 | LWJGL 通过 JNI 调用原生库；绑定 jar 目标字节码为 Java 8 | JNI 未被移除，**在 JDK 25 上可运行** |
| `sun.misc.Unsafe` 弃用路线（JEP 471 / JEP 498） | JDK 23 = 弃用（默认 `allow`，无告警）；**JDK 24 = 默认 `warn`（打印告警）**；JDK 26 起默认 `deny`（抛异常） | LWJGL 3.4.x 若走 Unsafe 内存路径，**在 JDK 25 上预计出现告警级输出（非错误、非异常，不阻断运行）** |
| 原生访问（restricted method） | JDK 24+（含 25）对外部函数/原生访问引入 `--enable-native-access`；未显式启用的模块会打印 restricted-method 告警 | 可能需 `--enable-native-access=ALL-UNNAMED` 消除告警；**确切文本以 M0 实测为准** |
| LWJGL 的应对 | 3.4.0 起支持 FFM API（`java.lang.foreign` 于 JDK 22 转正） | 存在「关闭 Unsafe 路径」的官方通道；是否默认走 FFM 由 LWJGL 运行期探测决定，非本项目可控 |
| 字节码目标 | 建议维持 `maven.compiler.release=21` | 见下「字节码目标裁决」 |
| Maven 版本 | **Maven 3.6.1 早于 JDK 25**，其默认插件版本过旧，且部分插件在新 JDK 上有反射访问告警 | **必须升级 Maven**（见下） |

**【结论 · JDK 25 下 LWJGL 的判定】**（明确结论 + 待实测项，不臆造）

1. **能否运行**：**能**。JNI 与 Unsafe 内存在 JDK 25 仍默认可用（JDK 26 才默认 `deny`），LWJGL 3.4.2 可在 JDK 25 LTS 下启动并创建 GL 上下文。
2. **告警级别**：预计为**告警（warning）而非错误**，共两类——(a) `sun.misc.Unsafe` 内存访问弃用告警（JDK 24 起默认 warn）；(b) 原生访问 restricted-method 告警。**两者均不阻断运行**，但会污染日志。
3. **是否需要 JVM 启动参数**：**作为稳妥默认，建议在启动脚本中显式加上这两个参数**（加了无害、可消除告警）；是否「必需」以 M0 实测文本为准：
   - `--enable-native-access=ALL-UNNAMED`（消除原生访问告警）
   - `--sun-misc-unsafe-memory-access=allow`（消除 Unsafe 内存访问告警）
   若 M0 实测**未出现**对应告警，则可移除相应参数，保留亦不影响运行。
4. **fat jar + .bat 场景的落地方式**：这两个参数是 `java` **启动器参数**，须放在 `-jar` **之前**，写进 `.bat` 脚本（见附录 B）；`java -jar target/skyisland.jar` 的手动运行方式需在发布说明中一并给出带参数的命令行。**不能**写进 `MANIFEST.MF`（Manifest 不支持 JVM 启动参数）。

**各口径实测矩阵（M0 执行）**：以下组合各跑一次并记录 stderr 文本与窗口行为。

| 组合 | 启动命令（M0 窗口 demo） | 预期 |
|------|--------------------------|------|
| A 裸跑 | `java -jar target/skyisland.jar` | 可运行；记录是否出现告警 |
| B 仅原生访问 | `java --enable-native-access=ALL-UNNAMED -jar ...` | 原生访问告警应消失 |
| C 仅 Unsafe | `java --sun-misc-unsafe-memory-access=allow -jar ...` | Unsafe 告警应消失 |
| D 全参数 | `java --enable-native-access=ALL-UNNAMED --sun-misc-unsafe-memory-access=allow -jar ...` | 告警最少；**若 D 与 A 行为一致且无异常，附录 B 默认采用 D** |

**【知识缺口 · 需 M0 实测验证】**：LWJGL 3.4.2 在 JDK 25 LTS 下的**确切告警文本**、是否需要上述参数、以及参数是否完全消除告警，超出可靠知识范围，**本文不臆造确切结论**。验证方法与判据见下表。

**M0 实测方法与判据（对应附录 C 的 V8/V9）**：

| 步骤 | 操作 | 观察点 | 通过判据 |
|------|------|--------|----------|
| 1 | 安装 JDK 25 LTS；`java -version` | 版本号 | 显示 `25` 且为 LTS |
| 2 | `mvn -v` | Maven 使用的 JDK | `Java version: 25`，Maven 3.9.9 |
| 3 | `mvn -q package` | 编译/打包是否报错 | `BUILD SUCCESS`，产出 `target/skyisland.jar` |
| 4 | **裸跑**（矩阵 A） | stderr 文本 | 窗口与 GL 3.3 Core 上下文创建成功；记录 `sun.misc.Unsafe` / `restricted method` / `Unsupported JNI version` 是否出现 |
| 5 | **带参数跑**（矩阵 D） | 与步骤 4 对比 | 告警消失或降级；窗口/上下文/输入/退出行为与步骤 4 一致 |
| 6 | 退出后检查进程 | 残留 | 无残留 `java` 进程 |

**判定**：只要步骤 4/5 中**窗口正常、GL 上下文创建成功、无 Error/Exception、无 JNI 版本不匹配、退出无残留**，即视为「**JDK 25 可用**」；告警是否出现只影响「是否保留启动参数」，不影响可用性判定。若步骤 4 出现**异常（非告警）**导致无法启动，则判定 **JDK 25 + LWJGL 3.4.2 不可用**，**回退**：以本机 **JDK 23** 为首版运行 JDK，并把该结论回报 PRD 第 12.6 节（触发口径再议）。

**字节码目标裁决（v0.3）**：

**【结论】维持 `maven.compiler.release=21`。** 理由：

### 1.6 fat jar 打包（maven-shade-plugin）要点

**【结论】** 用 `maven-shade-plugin` **3.6.0**，绑定 `package` 阶段，产出**替换主构件**的可执行 fat jar。

| 要点 | 设置 | 原因 |
|------|------|------|
| 版本 | 3.6.0 | 内置 ASM 9.7，支持 Java 23（v67）字节码；3.6.1 为更新版，可选 |
| `minimizeJar` | **`false`** | 最小化会误删 natives 与 `META-INF/services`，导致运行期找不到原生库 |
| 签名文件 | 排除 `META-INF/*.SF`、`*.DSA`、`*.RSA` | 重打包后签名失效会导致 `SecurityException` |
| 模块描述符 | 排除 `module-info.class` | 多个模块化依赖合并会冲突 |
| `ManifestResourceTransformer` | 设 `Main-Class` | `java -jar` 入口 |
| `ServicesResourceTransformer` | 合并 `META-INF/services` | 保留 SPI |
| 重定位（relocate） | **不做** | 重定位 `org.lwjgl` 无收益且有加载风险 |
| 多平台 natives | 只打 **单个平台**（Windows） | 避免把 linux/macos 的 `.dll` 一并塞入；跨平台发布时按平台各出一个 jar |
| `finalName` | `skyisland` | 产出稳定为 `target/skyisland.jar` |

关键配置片段：

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-shade-plugin</artifactId>
  <version>3.6.0</version>
  <executions>
    <execution>
      <phase>package</phase>
      <goals><goal>shade</goal></goals>
      <configuration>
        <createDependencyReducedPom>false</createDependencyReducedPom>
        <minimizeJar>false</minimizeJar>
        <shadedArtifactAttached>false</shadedArtifactAttached>
        <filters>
          <filter>
            <artifact>*:*</artifact>
            <excludes>
              <exclude>META-INF/*.SF</exclude>
              <exclude>META-INF/*.DSA</exclude>
              <exclude>META-INF/*.RSA</exclude>
              <exclude>module-info.class</exclude>
            </excludes>
          </filter>
        </filters>
        <transformers>
          <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
            <mainClass>com.skyisland.app.Main</mainClass>
          </transformer>
          <transformer implementation="org.apache.maven.plugins.shade.resource.ServicesResourceTransformer"/>
        </transformers>
      </configuration>
    </execution>
  </executions>
</plugin>
```

**预计体积**：Windows natives 合计约 30–60 MB，fat jar 约 40–80 MB，属正常范围。

**验收对齐（PRD M0）**：`mvn package` 零错误，产出 `target/skyisland.jar`；`java -jar target/skyisland.jar` 可直接启动；配套 `.bat` 双击可启动（脚本示例见附录 B）。

## 2. 「预留 Web」的真实边界（对应问题 2）

### 2.1 为什么 LWJGL 上不了浏览器

| 事实 | 结论 |
|------|------|
| LWJGL 是 **JNI 原生绑定** | 它调用本机 OpenGL/GLFW/OpenAL 动态库；浏览器沙箱内无 JNI、无本地动态库加载能力 |
| TeaVM / Bck2Brwsr 等 Java→JS 编译器 | 能把 JVM 字节码编译为 JS/WASM，但**不支持 JNI**，因此 LWJGL 绑定无法工作 |
| CheerpJ（商业） | 能在浏览器跑 Java 字节码，但**同样不提供 JNI 原生调用**，无法直接顶替 LWJGL |
| 原生 GLFW/OpenAL | 浏览器无对应宿主；窗口、输入、3D 音频均须换成 Web API（DOM/Canvas/WebGL/WebAudio） |
| 浏览器渲染 API | 只有 **WebGL / WebGPU**，与桌面 OpenGL 是不同的上下文与入口，着色器方言（GLSL ES）亦有差异 |

**【结论】** 只要技术上仍在用 LWJGL，浏览器端就不可能「原样跑起来」。任何「预留 Web」的说法都不能承诺代码可移植性，只能承诺**分层清晰**。

### 2.2 正确做法：分层 + 粗粒度后端接口

**结论**：把「平台相关」收敛到单一抽象层，游戏逻辑与渲染数据的生产完全不依赖 LWJGL。

分层（自上而下）：

| 层 | 内容 | 允许依赖 |
|----|------|----------|
| `app` | 启动、主循环编排 | 全部 |
| `game` | 玩法系统（生存、合成、成就、昼夜） | core/world/mesh/sim/ui |
| `sim` | 物理、实体、AI、战斗 | core/world |
| `world` | 区块、方块注册表、世界、光照 | core |
| `mesh` | 网格化（产出与渲染后端无关的顶点数组） | core/world |
| `ui` | 立即模式 UI（产出绘制指令列表） | core |
| `core` | 数学、容器、事件、时间 | 无 |
| **`platform`** | **接口：窗口/输入/图形/音频/时钟** | core |
| **`platform.lwjgl`** | **接口的 LWJGL 实现** | platform + `org.lwjgl.*` |

**强制规则（将写入控制清单，可 CI 校验）**：

> 全仓库中，`org.lwjgl.*` 的 `import` **只允许出现在 `com.skyisland.platform.lwjgl` 包内**；其余任何包出现即构建失败。

`platform` 层接口清单（首版范围，即「渲染后端抽象范围」的定稿）：

| 接口 | 职责 | 粒度 |
|------|------|------|
| `Window` | 创建/销毁窗口与 GL 上下文、事件轮询、`swap`、VSync、framebuffer 尺寸、全屏切换 | 粗 |
| `Input` | 键/鼠状态、光标模式、原始鼠标位移 | 粗 |
| `GraphicsDevice` | 创建/销毁 着色器、纹理（含纹理数组）、顶点缓冲与 VAO；**提交一批绘制命令** | **粗（按批）** |
| `AudioDevice` | 播放/停止音效与音乐、音量、距离衰减开关 | 粗 |
| `Clock` | 单调时间、帧时间 | 纯 Java |

**性能护栏（重要）**：抽象必须停在**「资源 + 批次」粒度**，**不得**下探到「每次 `glDraw*` 都过一次接口」的程度。热循环（逐顶点、逐 section 提交）留在 `platform.lwjgl` 实现内部，避免多态分派拖慢渲染。这样抽象层的运行期开销**近似为零**。

额外收益（即使永不上 Web 也成立）：可用**空实现后端**做无窗口自动测试（CI 无 GPU 也能跑仿真与单测），这是本设计的主要现实价值。

### 2.3 额外成本

| 成本项 | 量级 | 说明 |
|--------|------|------|
| 首版接口分层本身 | **约 2%–4%** 引擎工作量 | 与良好架构天然重合，不算浪费 |
| 若要真正出 Web 版 | **2–3 倍**额外引擎工作量 | 需重写渲染后端（WebGL）、平台层（DOM/WebAudio）、打包、且线程/内存模型大改（浏览器基本无自由线程、WebGL 无持久映射缓冲） |
| 数据与协议稳定性维护 | 持续但低 | 存档/网络协议作为「可移植契约」保持稳定 |

### 2.4 结论与将来路径

**【结论】** **不建议现在投入 Web 适配**。理由：

1. 浏览器不可运行 LWJGL，任何「Web 版」都等于**再写一遍渲染与平台层**，与首版「尽快跑通 60 FPS 体素》目标直接争夺资源。
2. Web 端缺失自由线程、持久映射缓冲、OpenAL 等，性能与手感都会显著退化，与「稳定 60 FPS」支柱冲突。
3. 首版的真正风险是「引擎能不能跑起来」，不是「能不能上浏览器」。
4. 只做**粗粒度接口分层**即可获得几乎全部架构收益（可测试性、可替换性），成本极低。

**将来真上 Web 的替代路径（按优先级）**：

| 路径 | 做法 | 评价 |
|------|------|------|
| **路径 A（推荐）** | 保留**存档格式与网络协议**作为稳定契约，用 Web 原生栈（TypeScript + WebGL2，或 Rust + `wgpu`/WASM）重写客户端渲染与平台层，直连 Java 主机 | 契约稳定则服务端与逻辑可复用，风险最低 |
| 路径 B | TeaVM/CheerpJ 编译逻辑层 + 自定义 WebGL 绑定 | 生态不成熟，绑定需自造，**高风险** |
| 路径 C | 云游戏串流桌面版 | 非「Web 版」，但成本最低、体验最接近原生 |

**对 PRD M5 交付项「渲染后端抽象接口（为 Web 预留）」的定稿理解**：交付物是 **2.2 节的接口集 + 唯一包约束的自动化校验**，**不是**任何 Web 运行能力。建议 PRD 将该项表述改为「平台抽象层落地：存在可插拔的 `Window/GraphicsDevice/Input/AudioDevice` 接口，且 `org.lwjgl.*` 引用集中于单一包」。M5 验收相应改为「接口存在且当前实现可插拔（新增空实现后端可编译通过）」。

## 3. 体素引擎核心方案（对应问题 3）

### 3.1 区块尺寸与内部分段

| 项 | 结论 | 理由 |
|----|------|------|
| 对外区块尺寸 | **16×16×128**（与 PRD 4.1 一致，不变） | 世界可见单位、存档单位；将来亦作为联机同步单位 |
| 内部分段 | **16×16×16 section，每区块 8 段** | 128 高整列一次性重建太贵；分段把「改一个方块」的重建代价从 O(32768) 降到 O(4096) |
| 存储单位 | 以 section 为最小存储与网格化单位 | 与后续 greedy/AO 处理边界一致 |

**结论**：**必须分段**。这是本引擎最重要的结构决策之一，将写入 ADR。

### 3.2 存储方式：调色板 + 位打包

| 方案 | 每 section 体积 | 评价 |
|------|-----------------|------|
| 原始 `byte[4096]`（blockId 直存） | 4 KB | 简单，但无法压缩，且未来扩展受限 |
| **调色板 + 位打包** | 4–4.5 KB（当前），扩展后仍平稳 | **【结论】采用** |

**结论**：采用 **Palette + 位打包（bit-packed `long[]`）**，每位条目位宽按调色板大小自适应（初始 4 bit 覆盖 16 种，超过则升到 5/6…8 bit，上限 8 bit 覆盖 256 种）。

体积估算：16×16×16 = 4096 格；4 bit → 2048 B，加调色板与元数据约 2.1 KB/section。

| 层 | 每 chunk（8 section） | 视距 6（13×13=169 chunk） |
|----|----------------------|---------------------------|
| 方块数据 | 约 17 KB | 约 2.9 MB |
| 附带（光照/脏标等） | 约 8 KB | 约 1.4 MB |
| **合计** | **约 25 KB** | **约 4.3 MB** |

**结论**：内存瓶颈**不在方块数据**（数量级仅几 MB），而在网格与纹理。这决定了优化资源应投向网格化与批量渲染。

### 3.3 网格生成策略

**结论**：**对不透明方块采用 greedy meshing；透明方块（水/玻璃等）走独立的非 greedy 面剔除通道。**

理由：

1. 空岛世界以**大面积平坦平台与箱体结构**为主（主岛面、地板、墙体、桥面），greedy 合并同类相邻面能成数量级削减四边形数。
2. 透明方块需独立排序与混合（back-to-front），本就不能与不透明合并，单独通道顺理成章。

分阶段落地（不违反「先跑通」目标）：

| 阶段 | 做法 | 目标 |
|------|------|------|
| M1 初期 | **面剔除**网格化（仅剔除被不透明白方块完全遮挡的面） | 尽快达到 60 FPS 可验收 |
| M1 后期 | 叠加 **greedy meshing**（不透明通道） | 顶点数下降，留出性能余量 |
| M3+ | AO 感知的 greedy 合并（见 3.4 与 4.2） | 视觉与性能兼顾 |

**面剔除规则**：对每个格子在 6 个方向检查邻居；邻居为「不透明实心」则剔除该面。邻居跨 section/跨 chunk 时，需查询相邻数据（网格化前先冻结当前 section 与其 6 邻居的快照），避免并发读写。

**AO 与 greedy 的冲突处理**：greedy 只能合并「方块类型、朝向、UV、AO 值均一致」的相邻面。**结论**：AO 不一致处不做合并；接受 AO 边缘合并率下降，换取 AO 正确性。把该约束写进网格化 Story 的验收标准。

### 3.4 纹理方案

| 方案 | 评价 |
|------|------|
| 单张大图集（atlas） | 需手工留 padding 防 mipmap 渗色，易出错 |
| **纹理数组 `GL_TEXTURE_2D_ARRAY`** | **【结论】采用**：每个方块贴图为数组一层，无 UV 渗色、无图集打包、mipmap 天然正确 |

**结论**：方块贴图用**纹理数组**，层索引即贴图 id，顶点携带层号；要求所有方块贴图尺寸一致（首版 **16×16**，程序生成零成本满足）。物品/UI 图标可用第二套数组或普通图集。过滤：**最近邻 + mipmap（含各向异性可选）**。

**知识缺口**：各向异性过滤扩展（`GL_EXT_texture_filter_anisotropic`）在不同驱动的最大支持值不一，需在 M1 运行期读取 `GL_MAX_TEXTURE_MAX_ANISOTROPY` 并夹取，不硬编码。

### 3.5 视锥剔除

**结论**：**做**，按 section（或 chunk 的合并 AABB）与 6 个视锥平面做 AABB–平面测试，剔除不可见网格。配合距离剔除（视距外卸载）与「邻居遮挡可选（首要面向 CPU 的快速路径）」使用。剔除在 CPU 侧每帧对可见集合做，成本 O(可见 section 数)，可忽略。

### 3.6 区块加载 / 卸载与线程模型

**结论**：**worker 线程池（`核数 − 1`）负责地形生成与网格化；GL 上传只在主线程。**

| 阶段 | 线程 | 说明 |
|------|------|------|
| 地形生成 | worker | 纯数据，无 GL |
| 网格化 | worker | 产出**堆外**顶点/索引缓冲快照 |
| GL 上传（VBO/VAO） | **主线程** | 主线程从队列取就绪网格，一次性上传 |
| 卸载（释放 VBO/VAO） | **主线程** | GL 资源释放必须在有上下文的线程 |

要点：

- **GL 单线程铁律**：GLFW/OpenGL 上下文绑定于主线程；任何 worker 调用 GL 都是未定义行为。将写入控制清单。
- 队列：距离优先（离玩家近的先网格化）；每帧限制上传数量（如 ≤ 4 个 section/帧）避免上传尖峰造成掉帧。
- 卸载迟滞：进入视距 +1 才开始加载，超出视距 +2 才卸载，避免边界抖动反复加载。
- 预算见第 8 章。

## 4. 渲染管线（对应问题 4）

### 4.1 基础设定

| 项 | 结论 |
|----|------|
| 图形 API | **OpenGL 3.3 Core Profile**（VAO、纹理数组、实例化均支持，兼容面广） |
| 深度 | 24 位深度缓冲；模板不需要 |
| 剔除 | 背面剔除开启；不透明按距离由近到远，透明由远到近 |
| MSAA | **默认关闭**（体素块状边缘无需抗锯齿），设置项可选 4× |
| VSync | 默认关闭（PRD 6.5），设置项可开（`glfwSwapInterval`） |

### 4.2 着色器职责

| 阶段 | 职责 |
|------|------|
| 顶点着色器 | 模型/视图/投影变换；传递贴图层号、UV、**AO 值**、**光照值（天光 + 块光）**、到相机的距离（供雾计算） |
| 片元着色器 | 从纹理数组采样；乘以 AO 与光照；按距离做雾混合；输出颜色 |

**结论**：光照与 AO 都在**顶点阶段插值**（每顶点烘焙），片元阶段只做采样与混合——这是体素常见做法，性能友好且效果足够。

### 4.3 光照方案

| 子系统 | 结论 |
|--------|------|
| **AO（环境光遮蔽）** | **做**。每面 4 个角按邻接三格采样计算遮蔽因子，烘焙进顶点属性。这是体素立体感的核心来源，不做会明显「平」。 |
| **平滑光照** | **做**（每顶点插值光照，避免逐面硬边） |
| **天光（sky light）** | 按列自顶向下传播，遇不透明白方块截断；夜晚全局乘 0.15 |
| **火把光** | 首版按 **PRD 4.4 的「固定径向衰减」** 实现（半径 6 格线性衰减），**不做** BFS 光传播 |
| 建议的后续迭代 | BFS 块光传播（天光 + 火把统一），作为「后续迭代」首个光照项 |

**【结论】** 首版光照 = **AO（做）+ 平滑插值（做）+ 天光列 + 固定径向火把衰减**。与 PRD 4.4 完全一致。附注（工程建议）：固定径向衰减在墙面/拐角会出现明显视觉断层，若 M4 有余量，优先把 BFS 块光列为第一优化项，可显著提升夜间观感且不改变 PRD 数值。

### 4.4 天空、雾、阴影

| 项 | 结论 |
|----|------|
| 天空 | 程序化渐变天空（天空盒/全屏 shader），颜色按昼夜阶段插值；太阳/月亮用广告牌；星星可选 |
| 雾 | **做线性雾**：从约 0.8×视距 起，到视距处完全过渡到地平线天空色，用于隐藏区块弹出 |
| 阴影贴图 | **首版不做**。成本高、体素场景收益有限，AO + 烘焙光照已提供足够深度信息 |
| 后处理 | 首版不做（无 Bloom/SSAO 等） |

**知识缺口**：全天时段天空色插值曲线需美术给出参考色；首版先用两组关键色（正午/午夜）线性插值，M4 再细化。

## 5. 物理与碰撞（对应问题 5）

### 5.1 玩家 AABB 与碰撞解算

**结论**：**逐轴分离解算（swept AABB per axis）**：先 X 位移并解算，再 Y，再 Z。这是体素碰撞的标准做法，稳定、易调试。

| 项 | 值 / 结论 |
|----|-----------|
| 玩家 AABB | 宽 **0.6**、高 **1.8**、中心位于脚上方 0.9 |
| 解算顺序 | X → Y → Z，逐轴推进并钳制 |
| 容差 | 碰撞检测留 epsilon（约 1e-3），避免贴面抖动 |
| 落地检测 | 本帧 Y 位移被向下阻挡且脚下方为实心 → 置 `onGround` |
| 自动上台阶 | **首版不做**（PRD 无台阶/半砖方块），跨 1 格需跳跃 |
| 潜行 | 降低移动速度，边缘防掉落（可选：潜行时不越出支撑边缘） |

**结论**：不做「穿墙容错」之类的额外机制；保持逐轴单步即可，负 Y 方向末速限制见 5.3。

### 5.2 方块射线拾取

**结论**：采用 **DDA 体素遍历（Amanatides-Woo）**，不是逐点步进。

| 项 | 值 |
|----|-----|
| reach | **5.0 格**（PRD 5.2，挖掘与放置共用） |
| 起点 | 相机位置（近平面附近，避免拾取到脚下） |
| 返回 | 命中格坐标 + 命中面法线 + 命中距离（供放置相邻空格与裂纹朝向） |
| 越界 | 命中 y∈[1,127] 之外或超出 reach 视为未命中 |
| 空手/持枪 | 挖掘/放置走「方块 DDA」；**开枪走 5.2.1 的 Hitscan 合并判定（不再「实体优先」）** |

#### 5.2.1 Hitscan 命中判定（PRD 12.2，v0.3 修正）

> **修正**：v0.2 曾表述「同一射线先测实体（怪物优先于方块）」，该表述**已废止**（PRD 12.2 明确「怪物优先于方块」为错误规则）。以下为正确口径。

**【结论】同一射线同时计算方块命中与实体命中，取沿射线距离最近的合法碰撞结果；不允许穿墙命中；最近命中为方块则记为方块命中（只出粒子、不结算伤害），仅当最近命中为实体时才结算伤害。**

实现口径：

| 要点 | 结论 |
|------|------|
| 两路求交 | 方块用 DDA（Amanatides-Woo）逐格推进，首个实心方块即得最近的方块命中参数 `t_block`（DDA 天然给出最小解、且命中即停）；实体用射线–AABB 求交（slab 法）逐个得 `t_entity` |
| 合并规则 | **取 `min(t_block, t_entity)` 为最终命中**。`t_entity < t_block` → 实体命中并结算伤害；`t_block ≤ t_entity` → 方块命中（粒子）。方块命中**天然阻断**其后的实体，故不会穿墙 |
| 早停 | DDA 一旦命中实心方块即停（无需继续推进）；实体遍历**只统计 `t_entity ≤ t_block` 且 `t_entity ≤ reach` 者**，超出者丢弃，无需完整排序 |
| 边界精度 | 射线–AABB 求交用 slab 法并留 `epsilon`（约 **1e-4**，与 5.1 碰撞容差同量级）；当 `|t_block − t_entity| < epsilon`（两者近似同时命中）时，**判方块命中优先**——方块是物理实体，避免贴墙怪物被「穿墙」判定 |
| reach | 仍为 **5.0 格**；两路求交均只接受 `t ≤ reach` 的结果 |
| 实体遍历加速 | **MVP 世界实体数很少（≤ 十几个），用暴力遍历即可**：对每个实体做一次射线–AABB。理由：暴力为 O(n)、n 极小，引入空间加速结构的维护成本与出错面远大于收益。**Alpha（M4）实体数显著上升时再评估**，届时第一候选为「每 tick 重建的均匀网格 / 三维网格」，不用 BVH |
| 零分配 | 遍历过程不产生堆分配（复用实体数组与临时向量对象池），与 8.5 稳态零分配一致 |
| 伤害结算 | 仅**最近命中为实体**时按 PRD 5.4 结算（含距离衰减）；方块命中不结算任何实体伤害 |

### 5.3 重力、跳跃、跌落伤害

| 参数 | 值 | 说明 |
|------|-----|------|
| 重力 g | **32 格/秒²** | 与 Minecraft 手感对齐 |
| 起跳初速 | **9.0 格/秒** | 跳跃高度约 1.25 格（可越 1 格） |
| 下落末速上限 | **50 格/秒** | 防止高速穿透；下落解算内部做子步 |
| 步进方式 | **固定 60 Hz**（累加器），渲染插值 | 决定性与将来联机一致性的基础 |
| 跌落伤害 | **`max(0, floor(坠落格数 − 3))`**（PRD 5.3） | 3 格内无伤，超出部分每格 1 点 |
| 虚空致死 | y < **−8** 直接死亡，不算普通跌落伤害（PRD 4.5/5.3） | 与跌落伤害互斥判定 |
| 跌落距离统计 | 起跳/离开地面时清零，落地结算 | 被弹开/缓降需重置 |

**结论**：物理用**固定 60 Hz 步进 + 渲染插值**，既为**将来联机**保留确定性基础，又避免高刷屏上的时间变异。子步（sub-step）只在下落速度接近末速时启用。

### 5.4 摄像机控制

| 项 | 结论 |
|----|------|
| 朝向 | 偏航（yaw）+ 俯仰（pitch）欧拉角；pitch 钳制 ±89°（防万向锁翻转） |
| FOV | 70（默认）→ 45（瞄准）；设置项 60–90（PRD 6.5） |
| 鼠标 | 原始位移驱动；灵敏度 0.1–2.0（PRD 6.5）；Y 轴可反转 |
| 准星 | 屏幕中心；瞄准态切换密集十字（PRD 5.4.3） |
| 视角与模型 | 第一人称仅相机；手持枪械模型独立于世界网格 |

## 6. 联机（后续迭代规划，首版不实现）

> **范围说明（v0.2）**：用户已裁决**首版不做局域网联机**。本章以下内容（权威模型、传输层选型、同步状态与频率、客户端插值与断线处理）保留为**后续迭代规划**，技术结论**不删除**，便于将来直接落地；但**不列入首版任何里程碑的交付与验收**。首版必须完成的最小架构预留见 **6.5**。

### 6.1 权威模型

**结论**：**主机权威（listen server）**。主机（房主）同时是世界模拟器与服务器；其余玩家是客户端。

| 对象 | 权威方 | 说明 |
|------|--------|------|
| 方块改动 | 主机 | 客户端提交意图，主机校验后广播 |
| 怪物生成/AI/位置 | 主机 | 客户端仅表现与插值 |
| Hitscan 命中 | 主机 | 客户端做表现反馈（对齐 PRD RK3） |
| 掉落物 | 主机 | 主机生成与结算 |
| 昼夜时间/刷怪 | 主机 | 由主机推进并同步 |
| 自身移动 | 客户端模拟 + 主机校验 | 局域网低延迟下最顺手；主机做速度上限/越界校验 |
| 自身生命/饥饿/背包 | 主机结算 + 客户端拥有 | 各自独立（PRD 7） |

**结论**：自身移动采用「客户端模拟 + 主机合理性校验」，这与 Minecraft 的模型一致，且在 2–4 人局域网下体验最好；世界与战斗严格主机权威。

### 6.2 传输层选型

**结论**：**Java 原生 TCP socket + Java NIO selector**，**不引入 Netty**。

| 方案 | 评价 |
|------|------|
| **原生 socket/NIO** | **【结论】采用**：2–4 连接、带宽极小（见下表），零额外依赖，无 natives 包袱 |
| Netty | 过度设计：管线、编解码、原生 epoll 在本场景无用；还多一个依赖进入 fat jar 与 shade 流程 |
| UDP | 仅用于**局域网房间发现广播**，不用于游戏数据（可靠性需求高） |

连接与线程模型：`ServerSocket` 接受连接；每连接一个**阻塞读取线程**（≤4 个，成本可忽略）；世界 Tick 在主逻辑线程驱动收发包；发送用长度前缀二进制帧（`[len:int][opcode:byte][payload]`）。握手包含**协议版本号**，不匹配即拒绝。

局域网发现：主机在 **UDP 25566** 周期性广播房间信息（名称/人数/端口）；客户端监听该端口列出房间；同时提供 PRD 6.4 的手动输入 IP 兜底（对齐 PRD RK8）。

### 6.3 同步状态与频率

| 状态对象 | 方向 | 频率 | 传输语义 |
|----------|------|------|----------|
| 自身位姿（位置/朝向） | C→S | 20 Hz | 覆盖式 |
| 其他玩家位姿 | S→C | 20 Hz | 覆盖式，客户端插值 |
| 怪物位姿 | S→C | 10–15 Hz | 覆盖式，客户端插值 |
| 方块改动 | C→S→全体 | 事件触发 | **可靠**（不可丢） |
| 掉落物 | S→C | 事件 + 5 Hz 位姿 | 可靠加覆盖 |
| 伤害/死亡命中 | C→S 意图，S→C 结算 | 事件触发 | 可靠 |
| 背包/快捷栏变更 | C↔S | 事件触发 | 可靠 |
| 生命/饥饿 | S→C | 事件触发 | 可靠 |
| 昼夜时间 | S→C | 1 Hz | 覆盖式 |
| 玩家加入/离开/迁移 | S→C | 事件触发 | 可靠 |

**带宽估算**：峰值远低于 100 KB/s（4 人），局域网毫无压力。

### 6.4 客户端插值与断线处理

**结论**：

- 其他实体用**快照缓冲插值**：客户端保留约 100 ms 的位姿快照，渲染时刻取「当前时间 − 100 ms」的插值结果；快照不足时最多外推 100 ms，之后冻结。
- 自身玩家：本地立即模拟（零延迟手感），主机侧仅做校验；若主机纠正则平滑回拉。
- 断线：主机保留该玩家实体与背包 **5 分钟**（对齐 PRD 7 掉线处理）；重连凭令牌恢复原位置与背包；超时后移除实体、物品留在原地。主机退出即保存并关闭房间，通知其他玩家「房主已离开」（对齐 PRD 7）。

### 6.5 为将来联机保留的最小架构预留（PRD v0.3 第 14.3 节对齐）

> 本节为 PRD v0.3 第 14.3 节与程基岩对齐的点。本节给出**明确结论**，不采用「二者皆可」的模糊表述。

**【结论】** 首版通过以下解耦，把「将来加联机」从「重写」降级为「接线」。以下为**必须在首版就做**的项，逐条给出成本与理由。

| 编号 | 必须做（首版即落地） | 成本 | 理由 |
|------|----------------------|------|------|
| P1 | 游戏逻辑与渲染/输入解耦：逻辑层不引用 `org.lwjgl.*`、不直读键鼠，只消费抽象输入事件 | **零成本** | 与第 2 章平台分层、唯一包约束天然重合，不额外写代码，只是规则约束 |
| P2 | 世界状态可序列化：区块/实体/玩家状态可无损写读，且与内存布局一致 | **零成本** | 存档（第 7 章）本就要做；联机同步只是复用同一序列化契约 |
| P3 | 固定时间步进与帧率解耦：逻辑以固定 60 Hz 累加器推进，渲染插值显示 | **零成本** | 物理（5.3）本就采用固定步进；确定性与单机手感同源 |
| P4 | 世界改动的单一入口：所有方块/实体变更经统一的「意图 → 应用」入口，而非散点直改 | **低成本** | 首版只需把改动收敛到一个方法；将来在该入口后插「本机应用 vs 发往主机」分支即可 |
| P5 | 状态快照与插值的显示层接缝：实体渲染位置取自可插值的状态容器，而非直接读模拟值 | **低成本** | 单机下为直通（等同当前值），不改变手感；将来换成 100 ms 快照缓冲即可（见 6.4） |
| P6 | 协议版本号占位：在存档/握手契约里预留 `protocolVersion` 字段与拒绝策略的位置 | **零成本** | 仅需在契约结构中留字段，首版不实现握手逻辑 |

**成本量级汇总**：P1 / P2 / P3 / P6 为**零成本**（本就随良好架构与存档产生）；P4 / P5 为**低成本**（各约 0.5%–1% 引擎工作量，仅是把既有直改改为经统一入口）。整体预留成本 **≤ 2%** 引擎工作量，与 2.3 节「接口分层约 2%–4%」同源、不重复计费。

**现在不该做的（避免为不存在的需求付成本）**：

| 不做项 | 原因 |
|--------|------|
| 实现 socket / NIO selector / 收发线程 | 无连接对象可接，纯空转；留待联机迭代（6.1–6.4 结论已备） |
| UDP 局域网发现广播 | 同上，且涉及防火墙放行等运行期问题（原 R08，现移入 9.2） |
| 客户端权威校验 / 回滚 / 补偿 | 单机无对手方，校验无对象；快照插值缓冲亦无必要 |
| 序列化协议的具体字段与压缩优化 | 契约形态未定（TCP 长度前缀帧见 6.2），过早固化字段会返工 |
| 把逻辑层改为「事件驱动 + 时间戳重放」的完全确定性架构 | 超出需求：首版固定步进 + 单一入口已足以将来接入，不必现在就付重放机制成本 |

**可验证验收口径（写入控制清单，可 CI 校验）**：

> **存在 P4 的统一「世界改动入口」接口，且全流程在单机（无网络）下可运行并通过既有玩法测试；`org.lwjgl.*` 引用集中于 `com.skyisland.platform.lwjgl` 单一包（对应 P1）。**

即：首版交付物须能证明「逻辑与渲染解耦、世界改动单入口、状态可序列化」三点成立，且**不包含任何联网代码**。

## 7. 存档（对应问题 7）

### 7.1 格式裁决（PRD Q5 的定调）

**结论**：**混合格式**——区块数据用**二进制**，元数据与玩家数据用**JSON 文本**。

| 数据类型 | 格式 | 理由 |
|----------|------|------|
| 区块地形（palette + 位打包 + 光照） | **二进制**（可选 Deflate/zstd） | 文本下体积爆炸且解析慢；二进制天然适配位打包 |
| `level.json`（版本、种子、游戏时间、里程碑、成就） | **JSON 文本** | 体积小、可人读、易做版本迁移与问题排查 |
| 玩家数据 | **JSON 文本** | 同上，且便于调试联机时的各自状态 |

**结论**：PRD Q5 的选项应由「二进制 vs 文本」改为「**混合：区块二进制 + 元数据 JSON**」。纯文本方案被否决（128 高 × 多区块的文本体积与解析开销不可接受）。

### 7.2 目录结构

```
saves/<worldName>/
  level.json          世界元数据 + 玩家列表 + 成就/里程碑
  level.json.bak      上一版元数据备份
  players/<uuid>.json 每个玩家独立状态（背包、快捷栏、当前枪械）
  region/r.<cx>.<cz>.bin  区域文件：一组区块的二进制块
```

### 7.3 区块二进制布局

```
[header]  magic(4B) | formatVersion(int) | chunkCount(int)
[record]×N
   record = length(int) | crc32(int) | sectionCount(byte) | payload
   payload = 每 section：paletteLen(varint) + palette(blockId 数组)
                         + bitsPerEntry(byte) + packedLongs(long[])
                         + 光照数组（可选，按位打包）
```

- 采用**调色板 + 位打包**与内存布局一致（3.2），落盘即内存镜像 + 压缩。
- 压缩：首版用 `java.util.zip.Deflater`（**零依赖**）；若 `lwjgl-zstd` 引入，可换 zstd 换更高压缩率。

### 7.4 原子性与损坏防护

**结论**：**临时文件 + fsync + 原子改名 + 保留 .bak + CRC32 校验**，四层防护。

| 措施 | 做法 |
|------|------|
| 先写临时文件 | 写 `xxx.tmp`，不直接改原文件 |
| 强制落盘 | `FileChannel.force(true)`（fsync）后再改名 |
| 原子改名 | `Files.move(tmp, target, ATOMIC_MOVE, REPLACE_EXISTING)`；Windows 同卷内原子 |
| 保留备份 | 覆盖前把旧文件改名 `.bak`；加载失败时回退 |
| 记录校验 | 每区块记录 CRC32 + 长度；加载时逐条校验 |
| 损坏恢复 | 单个区块损坏 → 记录日志；因地形**由种子确定性生成**，可从种子重建该区块；不可重建的（玩家改动）则该区块留空并告警 |

### 7.5 写入时机

| 时机 | 内容 |
|------|------|
| 自动保存 | 每 **60 秒** 一次（可配置） |
| 关键事件 | 昼夜结算（新一天）、玩家死亡、成就/里程碑达成、玩家加入/离开 |
| 退出 | 正常退出、主机关闭房间、返回主菜单 |
| 写入方式 | **异步**：快照脏数据 → 写盘线程处理 → 主线程不阻塞（避免卡帧） |

- 脏标记：只保存被修改过的区块（`dirty` 集合），未改动区块不重写。
- 顺序：先写区块数据，最后写 `level.json`（含递增的保存计数与时间戳），保证元数据「指向」完整数据。

### 7.6 `saveVersion` 与版本迁移（PRD 12.3，v0.3 新增）

**【结论】所有存档写入 `saveVersion`**（首版 = **1**），落在 `level.json` 顶层；区块二进制 header 保留 `formatVersion`（7.3）作为**存放格式版本**。二者职责不同：`saveVersion` 管「存档语义/契约版本」，`formatVersion` 管「二进制布局版本」。

| 环节 | 口径 |
|------|------|
| 写入位置 | `level.json` 顶层 `saveVersion`（int）；区块 `region/*.bin` header `formatVersion`（int） |
| 首版值 | `saveVersion = 1`；`formatVersion = 1` |
| 读取判断 | 先取 `saveVersion`：`== 当前` → 直接加载；`< 当前` → 走迁移链；`> 当前`（存档来自更新版本）→ **拒绝加载并提示** |
| 迁移策略 | 首版只有 v1，**迁移链为空**；但架构上预留逐级迁移的**函数表**（v1→v2→…），加载时按序应用。**禁止**「读取即隐式改结构」的迁移 |
| 不兼容提示 | 无法迁移或存档版本高于程序版本时，给出**明确中文提示**（如「该存档由更高版本创建，当前版本无法读取」/「存档格式不兼容，已保留原文件」），**不得静默失败或覆盖原存档** |
| 崩溃/失败回退 | 复用 7.4 的 `.bak` + CRC32：读取主文件失败 → 回退 `.bak`；仍失败 → 报错并保留现场，**不删除任何文件** |

> 具体「v1→v2 迁移什么」留待首次真发生格式变更时定义；本节只定**版本字段位置、判断顺序与迁移机制的存在性**。

### 7.7 稳定字符串 ID 与运行时索引映射（PRD 12.3，v0.3 新增）

**【结论】永久存档 ID 一律使用稳定字符串 ID（命名空间形式，如 `skyisland:stone`、`skyisland:iron_ore`、`skyisland:pistol`）；禁止用 enum ordinal 或数组下标作为永久存档 ID。** 运行时热路径用**数值索引**，存盘/配置/将来的网络契约用**字符串**，二者由一张**注册表映射表**连接。

| 项 | 口径 |
|----|------|
| 字符串 ID 形态 | `<namespace>:<path>`，本项目 namespace 固定 `skyisland`；path 用小写下划线（`iron_ore`） |
| 存储内容 | 存档、配方、配置、将来的网络协议**只写字符串 ID** |
| 运行时形态 | 区块调色板、方块数组、物品槽等热路径用**数值索引（int/short）**，避免逐帧字符串哈希与比较 |
| 映射表 | 启动期构建**双向映射**：`String→int`（解析存档/配置用）与 `int→String`（存盘/调试用）两张表（或一个含双索引的注册表对象）。**索引在单次运行内稳定，但不承诺跨运行/跨版本稳定**——这正是禁止用它存盘的原因 |
| 注册时机 | 方块/物品/枪械/弹药/怪物在注册表注册时分配索引；**同一字符串 ID 重复注册视为配置错误，启动即失败并报错** |
| 未知 ID 处理 | 读档遇未知字符串 ID → 记录日志，**降级为占位方块/丢弃物品**并提示，**不得崩溃**；占位与重建规则与 7.4 区块重建一致 |
| 索引宽度 | 方块/物品索引各预留 ≥ 256；与 3.2 调色板位宽（≤ 8 bit）兼容 |

> 该契约是数据驱动（7.8）与将来联机同步的共同基础：**字符串 ID 是跨版本、跨进程、跨机器的稳定标识；数值索引是本进程内的加速句柄。**

### 7.8 数据驱动的模块边界（PRD 12.4，v0.3 新增）

**【结论】以下八类数据走 JSON 配置、与代码解耦；本轮只定「哪些做成数据、边界在哪」，不展开 schema（schema 细节留待 `docs/TECH_DESIGN.md`）。**

| 配置类 | 运行时对应 | 边界（本轮定稿） |
|--------|-----------|------------------|
| Block（方块） | 方块注册表 + 方块状态位 | 每种方块一条：稳定 ID、显示名、纹理层、是否实心/透明、硬度、光照属性、是否有状态位（如木门开合、火把朝向） |
| Item（物品） | 物品注册表 | 稳定 ID、显示名、图标、堆叠上限、是否方块物品（引用 Block ID） |
| Gun（枪械） | 武器参数 | 稳定 ID、伤害、弹匣、射速、换弹时长、距离衰减、散布 |
| Ammo（弹药） | 弹药类型 | 稳定 ID、显示名、适配枪械（引用 Gun ID） |
| Recipe（配方） | 合成系统 | 输入（物品 ID + 数量）× 输出（物品 ID + 数量） |
| Monster（怪物） | 实体/AI 参数 | 稳定 ID、生命、伤害、速度、掉落表 |
| ThreatLevel（威胁等级） | 刷怪强度 | 等级 → 刷怪上限 / 构成 / 间隔 |
| ResourceDistribution（资源分布） | 岛屿资源生成 | 岛屿 → 方块构成 / 权重 / 再生参数 |

**边界规则**：

- **数据只描述「是什么 + 数值」，不描述「怎么做」**：行为（AI 决策、合成判定、渲染）留在代码；配置**不得**引入可执行逻辑。
- **一切跨引用字段一律用稳定字符串 ID**（7.7），不用内部索引。
- **配置在启动期加载并校验**（引用完整性、数值范围），校验失败即启动失败并给出可读错误。
- **schema 细节（字段名、类型、默认值、版本字段）留待 `docs/TECH_DESIGN.md`**，本轮不写、不冻结，避免过早固化。

## 8. 性能预算（对应问题 8）

### 8.0 性能验收基准与集成显卡硬约束（PRD 12.5，v0.3 新增）

**基准环境（实测，直接采用）**：Intel Core i5-13500H（16 线程）/ 15.7 GB / Windows 11（10.0.26200）x64 / **Intel 集成显卡（Iris Xe 级）**。独显状态未探明，标注「待 M0 实测补全」。

**判定口径（硬约束）**：

| 项 | 口径 |
|----|------|
| 测试条件 | 1920×1080、Windows、**Release 构建**、**VSync 关闭**、默认视距 **6 区块**、标准测试世界、正常怪物数量（不超过 Threat Level 上限） |
| 测试时长 | MVP 阶段（M0–M3）≥ 5 分钟；Alpha 与 RC（M4/M5）≥ 10 分钟 |
| 判定指标 | 测试时长内 **第 95 百分位帧时间 ≤ 16.7 ms**，且**不得出现 > 50 ms 的 GC 卡顿** |
| 门禁 | **「视距 6 区块 + 集成显卡 60 FPS」为 M1 门禁**（PRD 12.5）；只写「60 FPS」而无基准环境视为无效验收 |

**【结论 · 关键判定】1920×1080 + 视距 6 + 集成显卡（Iris Xe 级）→ 第 95 百分位帧时间 ≤ 16.7 ms：判定为「现实，但余量薄、风险中高」。**

判断依据：

1. **GPU 侧可达**：MVP 体素世界以**不透明地形**为主（MVP 13 种方块**不含水**，透明仅玻璃、量少），配合面剔除 + greedy + 距离雾剔除，overdraw 低；着色为「纹理数组采样 + 顶点烘焙光照/AO + 线性雾」的简单前向着色，无阴影、无后处理。Iris Xe 级 iGPU 在 1080p 下渲染该复杂度场景**在能力范围内**。
2. **风险集中在 CPU 侧与 GC，而非 GPU**：iGPU 与 CPU **共享系统内存与带宽**，真正的掉帧源更可能是**主线程网格化尖刺、区块加载卡顿、每帧分配触发的 GC**——这些是 **P95 帧时间（而非均值）** 的主要威胁。故 3.6 的线程模型、8.3 的上传节流、8.5 的稳态零分配是本指标能否达成的**决定性因素**，优先级高于 GPU 侧优化。
3. **余量薄的原因**：iGPU 无独立显存、带宽受限，且 15.7 GB 为共享内存；P95 口径对尖刺敏感。故必须**以 M1 实测为准**，不得凭推断签署达标。

**降级阶梯（若 M1 实测不达标，按此顺序执行，逐级确认）**：

| 优先 | 手段 | 说明 | 代价 |
|------|------|------|------|
| 1 | **降低内部渲染分辨率**（1080p 渲染到 1600×900 / 1440×810 的 framebuffer，再上采样到窗口） | 直接缓解 iGPU 填充率压力；体素低多边形下画质损失可接受 | 轻微模糊；实现成本低（改 framebuffer 尺寸 + 全屏 blit） |
| 2 | **降视距 6 → 5**（必要时 → 4） | 线性削减可见 section 数与网格量 | 视野变小、雾更近；**直接改变 PRD 参数，需 PRD 同步** |
| 3 | **降低网格复杂度**（AO 先降为每面统一值、暂缓各向异性过滤） | 减顶点属性与片元成本 | 观感变平 |
| 4 | **分区渲染 + 合并提交**（可见 section 聚成少量 MultiDraw，减少状态切换） | 优化 CPU 提交，不直接降 GPU 填充 | 引擎工作量 |
| 5 | 以上仍不达标 | **回报主理人，触发 PRD 12.5 基准再议**（例如把门禁基准改为 1600×900） | 属规格变更 |

> 取舍原则：**优先牺牲分辨率，最后才动视距**——分辨率是「整体线性成本」，视距是「世界尺度与玩法可玩性」，后者牵动 PRD 设计参数，改动代价更高。

### 8.1 帧预算

| 项 | 目标 |
|----|------|
| 帧率 | **稳定 60 FPS**（PRD 4.1）；判定以 **P95 帧时间 ≤ 16.7 ms**（8.0）为准，非均值 |
| 单帧预算 | **16.7 ms**（P95 上限） |
| 主线程分配 | CPU 逻辑（物理/AI/输入）≤ 3 ms |
| 提交/剔除 | CPU 渲染准备 ≤ 3 ms |
| GPU | 其余时间；**集成显卡目标 GPU 帧时间 ≤ 12 ms**（为共享带宽留余量） |
| 帧时间尖刺 | **单帧 > 33 ms 须定位**；**任何 > 50 ms 的 GC 卡顿直接判不达标**（8.0） |
| 均值陷阱 | 均值 ~16.7 ms 但 P95 超限 → **仍判不达标**（防均值达标掩盖尖刺） |

### 8.2 内存预算

| 类别 | 上限 | 说明 |
|------|------|------|
| 堆（`-Xmx`） | **2 GB** | 对象、地形生成、JSON；**集成显卡与 CPU 共享全部内存，堆不得再上调** |
| 原生/堆外（LWJGL） | **≤ 384 MB**（由 512 MB 收紧） | 网格顶点缓冲、纹理（含 mipmap） |
| 方块数据（视距 6） | 约 4.3 MB | 见 3.2，可忽略 |
| 纹理 | **约 32–128 MB**（由 64–256 收紧） | 首版方块贴图 16×16、层数少（13 种方块），纹理数组实际占用远低于旧上限；**iGPU 无独立显存，纹理占用与带宽直接竞争系统内存** |
| 网格顶点 | **约 80–200 MB**（由 100–300 收紧） | 依赖 greedy 效果与可见量；共享带宽下应尽量压小 |

**【结论】集成显卡约束下，内存预算整体收紧**：iGPU 与 CPU 共享系统内存与带宽，实际可用显存由驱动动态分配，**不得按「存在独立显存」规划**。启动参数维持 `-Xms2G -Xmx2G`（固定堆，避免扩堆抖动），**禁止**在集成显卡目标机上把 `-Xmx` 上调。GC 选型见 8.5（以 M1 实测为准）。

### 8.3 网格化与加载耗时

| 项 | 目标 | 依据 |
|----|------|------|
| 单 section（16³）网格化 | **≤ 3 ms** | 4096 格 × 6 面邻接检查 |
| 单 chunk（8 section） | **≤ 20 ms** | 单 chunk 的一次重建上限 |
| 单帧 GL 上传 | **≤ 4 个 section** | 平滑上传，避免尖峰 |
| 首次进入世界（169 chunk，12 核 16 线程） | **≤ 2 秒** | 169 × 20 ms / 11 worker ≈ 0.3 s，留余量 |
| 区块弹出 | 不可见（雾 + 距离卸载掩盖） | 见 4.4 |

**结论**：worker 数 = `max(1, 核数 − 1)`，把主线程留给渲染与物理。**单 section 网格化 ≤ 3 ms 与每帧 GL 上传节流（≤ 4 section）是保住 P95 帧时间的主要防线**（8.0）：网格化在 worker 完成，主线程仅做节流后的上传，避免把 CPU 尖刺打进帧内。上传节流写入控制清单。

### 8.4 Draw Call 预算

| 层级 | 目标 |
|------|------|
| 常规（逐 section 提交 + 视锥剔除） | **≤ 200 draw calls/帧** |
| 优化后（`glMultiDrawElementsBaseVertex` / `glMultiDrawArraysIndirect`） | **< 50** |
| 材质通道 | 不透明通道 + 透明通道 + UI 通道，各 1 个批次概念 |

**结论**：以「每 chunk / 每区域一次 MultiDraw」为优化方向；169 chunk 若不批处理可达 1300+ draw（超预算）。**集成显卡下驱动开销与状态切换同样敏感，故 MultiDraw 不是可选优化而是达标必需**（视锥剔除后仍可能有 600–700）。据此锁定：Draw Call 目标常规 ≤ 200、优化后 < 50。

**集成显卡附加约束**：iGPU 的瓶颈常在**填充率与带宽**而非纯 draw call 数，故除控 draw call 外还须：**严格背面剔除、不透明由近及远（Early-Z 友好、减少 overdraw）、透明（玻璃）由远及近且量小、避免任何全屏后处理**。

### 8.5 GC 压力控制

**结论**：**稳态零分配**是硬指标。

| 措施 | 说明 |
|------|------|
| 热路径零分配 | 物理/AI/渲染循环内不 `new`、不装箱、不用流式 API、不用 `String` 拼接 |
| 缓冲复用 | 顶点/索引用堆外 `MemoryBuffer`，复用与池化 |
| 集合复用 | 用原始类型数组与对象池替代临时集合 |
| 字符串 | 预格式化、缓存 |
| GC 配置 | G1（或 ZGC），目标暂停 < 10 ms，GC 时间 < 帧预算的 2% |
| 度量 | F3 调试面板显示分配速率与 GC 次数；纳入每里程碑性能回归 |

**知识缺口**：G1 与 ZGC 在本项目的具体表现需实测；JDK 25 默认 GC 为分代 ZGC（低暂停、吞吐略低），与 G1 择一以 M1 实测数据决定（结合 8.0 的「> 50 ms GC 卡顿」判据，不预先写死）。

## 12. MVP 范围削减对技术架构的影响（PRD v0.3 第 9/10 章，v0.3 新增）

> **前置**：PRD v0.3 的 **MVP = M0–M3**，Alpha = M4（第 9/10/11 章）。本节把「MVP 范围」翻译成技术侧的两张清单——**可延后**与**必须现在做对**——并给出 MVP「无联网代码」的落地要求。

### 12.1 MVP 范围摘要（技术视角）

MVP（M0–M3）：主岛 **32×32** + **1 座资源岛（石矿岛，(48,0)，14×14）**；**13 种方块**；**只手枪 + 1 种弹药（手枪弹）**；**只 1 种近战怪**；**7 条配方**（R01/R02/R03/R06/R07/R08/R11）；**无饥饿**、无农业、无成就、无沙子重力、无铜/金/晶体；基础背包、基础昼夜、夜间刷怪、基础 Save/Load、石矿岛简化版资源核心。

### 12.2 因此可以延后到 Alpha 的技术模块（逐条判断）

| 模块 | MVP 是否删去对应玩法 | 技术判断 | 理由 |
|------|----------------------|----------|------|
| **农业 / 作物生长 tick** | 是（10.3 明确 Alpha） | **延后到 Alpha** | 无耕地/小麦种/食物，故**不需要**定时作物状态机、生长阶段数据与随机 tick 调度器 |
| **多枪械的武器状态机泛化** | 是（MVP 只手枪） | **延后到 Alpha**，但接口留缝 | MVP 只手枪：武器可先写成**单实例、参数数据驱动**（见 12.3 必须项），但**不为 4 把枪预写分支**；Alpha 再把「参数来源」从单条配置扩为表 |
| **多怪物 AI 分支** | 是（MVP 只 1 种近战怪） | **延后到 Alpha** | MVP 只需「追近 + 近战」一条 AI 路径；远程枪手、大型怪、冲锋怪的分支与寻路增强留到 Alpha |
| **完整光照传播（BFS 块光）** | 是（MVP 固定径向火把衰减） | **延后到 Alpha** | MVP 保持 4.3 的「AO + 平滑插值 + 天光列 + 固定径向火把」，不实现 BFS 传播；夜间观感断层留待 Alpha 首个光照优化项 |
| **全岛资源再生 / 复杂资源分布** | 是（MVP 只石矿岛简化核心） | **延后到 Alpha** | MVP 只做 1 个简化资源核心；多岛再生调度留到 Alpha |
| **饥饿系统** | 是 | **延后到 Alpha** | 无饥饿 → 不需要饥饿 tick、消耗/恢复曲线与饥饿 UI |
| **成就系统 / 探索度** | 是 | **延后到 Alpha** | 无成就 → 不需要事件订阅与成就持久化 |
| **沙子重力 / 方块更新级联** | 是（PRD 14.4 Q3 归 Alpha） | **延后到 Alpha** | MVP 方块无需下落；**但需为方块状态位预留**（见 12.3） |
| **多弹药类型** | 是（只 1 种） | **延后到 Alpha** | 弹药可先单条，结构上按「类型表」设计即可 |
| **完整音效 / 粒子系统** | 是 | **延后到 Alpha**（保留最小反馈） | MVP 只需挖掘/开枪/命中的最小反馈；完整音效与粒子池化留 Alpha |
| **威胁等级 TL1–TL4** | 是（MVP 只 TL1） | **延后到 Alpha** | MVP 固定 TL1 刷怪参数 |
| **多岛生成（森林/金属/晶矿）** | 是 | **延后到 Alpha** | 世界生成保留「可参数化多岛」的接口，但 MVP 只实例化主岛 + 石矿岛 |

**统一说明**：以上模块**代码不写**（不预置空实现分支），仅在**数据结构与接口**上避免「写死到无法扩展」。这是「延后」而非「预留代码」——与 6.5 的联机预留不同，后者是零成本契约，此处连契约都可等 Alpha。

### 12.3 必须现在做对、否则 Alpha 要返工的模块

| 模块 | 为什么现在必须做对 | 落地口径 |
|------|--------------------|----------|
| **方块/物品的数据驱动契约** | 13 种方块若硬编码，Alpha 扩到多岛多方块需全面重构 | 方块/物品走 JSON 配置（7.8）；**行为在代码、数值在配置** |
| **稳定字符串 ID** | 存档一旦用 ordinal/下标，Alpha 增删方块即错位、旧档全废 | 7.7：`skyisland:stone` 形式；注册表映射表；严禁 ordinal/下标入档 |
| **存档 `saveVersion`** | 首版不写版本字段，Alpha 改格式将无法迁移/判断 | 7.6：`saveVersion=1` + 迁移函数表接口；写入位置与拒绝口径定死 |
| **方块状态位** | 木门开合、火把朝向若没有状态位，Alpha 加沙子重力/更多状态方块要改存储布局 | 3.2 调色板 + 位打包的 section 存储**预留方块状态位**（每格除方块 ID 外可带状态）；MVP 只用到门/火把 |

| **世界改动单一入口** | 散点直改，Alpha 与将来联机都要返工 | 6.5 P4：统一「意图 → 应用」入口 |
| **固定时间步进 + 渲染插值** | 逻辑与帧率耦合，Alpha 加更多系统会引入时序 bug | 5.3：固定 60 Hz 累加器 |
| **配置启动期校验** | 配置错误若延到运行期才暴露，Alpha 内容变多后排错困难 | 7.8：引用完整性/数值范围启动即校验，失败即启动失败 |
| **集成显卡性能基线** | 若 MVP 就超预算，Alpha 加枪/怪/粒子必然崩 | 8.0：M1 即按「视距 6 + iGPU + P95 ≤ 16.7 ms」门禁 |

### 12.4 MVP 阶段「无联网代码」与最小架构预留的落地要求

**【结论】MVP 及整个首版（M0–M5）不得引入任何联网代码。** 具体口径：

| 要求 | 说明 |
|------|------|
| 禁止项 | 不引入 socket / NIO selector / 收发线程 / UDP 广播 / 任何网络库（Netty 等）；不使用 `java.net.*` 做游戏数据通信 |
| 保留项（零成本，6.5 P1–P3 / P6） | 逻辑与渲染解耦（P1）、世界状态可序列化（P2）、固定步进（P3）、契约预留 `protocolVersion` 占位字段（P6）——**均随良好架构与存档天然成立，不额外写代码** |
| 保留项（低成本） | 世界改动单一入口（P4）、状态快照与插值的显示层接缝（P5）——各约 0.5%–1% |
| 验收口径 | 首版交付物须能证明「逻辑与渲染解耦、世界改动单入口、状态可序列化」，且**全流程在单机（无网络）下可运行并通过玩法测试**；`org.lwjgl.*` 引用集中于 `com.skyisland.platform.lwjgl` 单一包 |
| 成本 | 整体 **≤ 2%** 引擎工作量（6.5），不增加任何首版功能 |

> 说明：12.2「延后到 Alpha」的模块与「无联网」是两条独立边界——延后指**玩法功能**，无联网指**传输层**；二者都不影响 P1–P6 的零成本契约。

## 附录 B：Windows 启动脚本参考

`run.bat`（与本机 JDK 路径绑定的稳妥版）：

```bat
@echo off
setlocal
set DIR=%~dp0
"C:\Program Files\Java\jdk-25\bin\java.exe" ^
  -Xms2G -Xmx2G -XX:+UseG1GC ^
  --enable-native-access=ALL-UNNAMED ^
  --sun-misc-unsafe-memory-access=allow ^
  -Dfile.encoding=UTF-8 ^
  -jar "%DIR%skyisland.jar" %*
endlocal
```

`run.bat`（依赖 PATH 中 java 的通用版）：

```bat
@echo off
setlocal
set DIR=%~dp0
java -Xms2G -Xmx2G -XX:+UseG1GC ^
  --enable-native-access=ALL-UNNAMED ^
  --sun-misc-unsafe-memory-access=allow ^
  -Dfile.encoding=UTF-8 ^
  -jar "%DIR%skyisland.jar" %*
endlocal
```

**说明**：`-Xms/-Xmx` 固定 2 GB（8.2，集成显卡下不得上调）；`-Dfile.encoding=UTF-8` 防中文乱码；`--enable-native-access=ALL-UNNAMED` 与 `--sun-misc-unsafe-memory-access=allow` 为 **JDK 25 下消除 LWJGL 告警的稳妥默认**（是否必需以 M0 实测为准，见 1.5 的矩阵 A/D）；二者是 JVM 启动参数，**须置于 `-jar` 之前**；natives 由 LWJGL 自动提取，脚本无需配置 `java.library.path`。
