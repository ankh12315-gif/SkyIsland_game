## A′. 技术栈口径的正式裁决

### A′.1 字节码目标与 API 基线（关闭 T-3）

**裁决（正式，不再讨论）：**

| 项 | 值 |
|---|---|
| 构建 / 开发 JDK | **JDK 25** |
| `maven.compiler.release` | **21** |
| SkyIsland 产品代码 | **不得直接依赖 Java 21 之后才存在的 API** |
| 本项目对 `java.lang.foreign` / FFM | **不直接使用** |
| LWJGL 内部 native 实现 | 属第三方内部实现；**不因此要求产品代码升级到 release 25** |

**理由（记录判断，避免反复）：**

1. 游戏本身没有使用 FFM 的产品需求。为了输入测试或其他辅助能力把整个运行基线锁死到 Java 25，
   没有收益，并降低后续发行兼容性。
2. 反过来，把 `release` 提到 25 会**把运行环境与 JDK 25 绑定**，直接冲突 PRD 12.6
   「字节码目标与运行 JDK 解耦」的目标。
3. M0 遇到的具体障碍（`java.lang.foreign` 在 `--release 21` 下是预览 API，默认禁用）
   **已经用进程外方案绕过**，不再构成阻塞。

> **落地检查手段**：如果 M1 之后有人试图在 `src/main` 里 `import java.lang.foreign.*`，
> 构建会直接失败（预览 API 默认禁用）。**这个失败是期望行为，不是缺陷。**

### A′.2 native-access 参数（关闭 T-4）

M0 实测（`M0_REPORT.md` §3.3）：

| 启动参数 | stderr 字节 | J-1 `System::load` 受限方法 | J-2 `Unsafe::objectFieldOffset` 弃用 |
|---|---|---|---|
| 默认（空参数集） | 866 | 出现 | 出现 |
| `--enable-native-access=ALL-UNNAMED` | **429** | **消失** | 仍出现 |

**裁决：**

1. **开发 / 测试启动脚本默认加入 `--enable-native-access=ALL-UNNAMED`。**
   （`run-m0.bat`、`run-m1.bat` 已写入；见 §A′.4）
2. 性质是**消除 JDK 25 的 native-access 告警**，**不是** SkyIsland 的游戏逻辑依赖。
   产品代码不得依赖该参数的存在——即：**去掉它游戏必须仍能正常运行**。
3. **不尝试**通过 JVM 参数隐藏 LWJGL 的 `sun.misc.Unsafe` 告警：实测无任何参数可抑制，
   它由 LWJGL 3.4.3 的内存后端选择决定（WATCHLIST，见 §U′）。
4. 最小参数集仍是**空集**——上述参数是"噪音治理建议"，不是"运行必需"。

### A′.3 M1 输入层的两处必改（E-6 / E-7）

#### E-6：退出键必须是边沿触发

M0 的退出路径是 `pollEvents()` 内 `input.isKeyDown(GLFW_KEY_ESCAPE)` —— 这是一个**电平**判定。
当"按下"与"抬起"落在**同一个 `glfwPollEvents()` 批次**内时（注入输入必现；人手极快点按也可能），
批次结束后 `keyDown[ESCAPE]` 已经回到 `false`，**这次按键被完全漏掉，窗口不会关闭**。

> **实测证据**：`PRE_M1_CLOSURE.md` §2 的 T-2 探针中，ESC 的 PRESS 与 RELEASE
> 时间戳均为 `19.423`（同一毫秒），程序未退出，直到 90 秒后被外部终止。

**M1 起规则**：所有"按一下触发一次"的动作键（ESC 退出、F3 调试、数字键切槽、F5 存档等）
**一律使用按下沿（edge）判定**，实现方式为在回调中置"本帧按下过"标志，逻辑步消费后清零。
**电平判定只允许用于"持续按住"的意图**（WASD 移动、左键挖掘）。

#### E-7：不可映射的键必须被记录

`InputState.onKey` 原本对 `key < 0 || key >= KEY_TABLE_SIZE` 直接 `return`，不产生任何日志。
后果是两种完全不同的根因产生一模一样的观测（日志里什么都没有）：

- (a) 事件根本没到达窗口过程；
- (b) 事件到达了，但 GLFW 无法把该 scancode 映射为键码。

**M1 起规则**：不可映射的键**必须记录**（标记 `key=UNMAPPED` 并附 scancode），
并单独计数（`unmappableKeyEventCount`）。**测量环节不允许静默丢数据**——
这条与 §C.4′ 第 1 条同源。

## C.4′ Performance Measurement Contract（取代 v0.1 §C.4 的缓冲实现）

> **本节是硬约束，不是建议。** 任何性能数字若违反其中一条，该数字**作废**，
> 不得用于 Gate 判定、不得用于跨里程碑外推。

M0 的教训是：**首轮运行的三项宣称（"统计了 60 秒"、"FPS 远高于 60"、"无卡顿"）全都是错的。**
三条都不是引擎的错，而是**测量仪器不可信**。因此把仪器本身的规定提升为合同条款。

| # | 条款 | 反例（M0 真实发生过） |
|---|---|---|
| **1** | **性能统计必须覆盖完整 measure window。** 声明的统计窗口与实际覆盖的时长必须一致，且可自证（如同时输出 `计划测量时长` 与 `实际统计窗口`） | 声称统计 60 秒，实际只覆盖最后 4.3 秒 |
| **2** | **不允许固定容量 ring buffer 导致只统计窗口末尾。** 统计结构的内存占用必须**与窗口长度无关**（定宽直方图或等价结构） | 环形缓冲容量 3600，在 836 FPS 下只够 4.3 秒 |
| **3** | **P95 / P99 必须基于完整窗口的 histogram 或等价可靠方法。** 必须声明分位数的分辨率，且该分辨率相对判定阈值有数量级余量 | 用末尾 4 秒的分位数冒充 60 秒 |
| **4** | **FPS 必须由完整 frame count / elapsed time 计算**，不得使用会被容量截断的计数 | `fps = count / elapsed`，`count` 被截断 → 报出衰减假值 **59.98**（真实约 836），**恰好会把"FPS ≫ 60"这条门禁误判为不及格** |
| **5** | **raw frame delta 与 clamped logic delta 必须分开统计。** 交给统计的必须是**未经钳制**的真实帧间隔 | 用钳制后的 delta 统计，把一次 1.376 秒的真实停顿**伪装成"刚好 250 ms"** |
| **6** | **clamp count 必须独立记录**，与 spike count 并列输出 | 钳制次数被淹没在帧统计里，无法区分"停顿"与"停顿被截断" |
| **7** | **测试脚手架不得同步运行在 game loop 内制造假卡顿。** 注入 / 合成 / 采样等辅助动作必须在 loop 之外执行 | AWT Robot 合成在主循环内同步执行约 1 秒 → 凭空造出 **250 ms 级 spike + logic 步欠账**，测试污染被测量对象 |
| **8** | **warm-up 数据不得进入正式统计。** 预热结束必须重置统计；输入统计也必须一并重置 | 输入统计未重置，混入建窗之前的事件 |
| **9** | **OS / environment spike 与持续引擎卡顿必须区分。** 判定"卡顿"必须给出分布证据（如 P99），并要做对照实验 | `>50 ms` 帧数 0–34 波动，若不区分就只能在"引擎有问题"和"环境有问题"之间猜 |
| **10** | **M0 的 FPS 不得作为 M1 / M2 / M3 性能的外推依据。** M0 没有任何游戏内容，其 845–1596 FPS 只说明"基础设施本身开销低" | 把 800–1500 FPS 当成 M1 的目标基线 |

### C.4′.1 已落地的实现（M0 已修，M1 沿用）

| 条款 | 实现 |
|---|---|
| 1 / 2 / 3 | `FrameStats` 改为**定宽桶直方图**：`BUCKET_MS = 0.1`，`BUCKET_COUNT = 2000` + 1 个溢出桶。内存恒定 ≈ 8 KB，覆盖任意长度窗口，分位数误差 ≤ ±0.1 ms（判定阈值 16.7 ms 相对它有 167 倍余量） |
| 4 | `fps = frameCount / Σ帧间隔` |
| 5 / 6 | `recordFrame(rawDelta)` 记录**未钳制**值；`GameLoop` 另调 `recordClamp()`；摘要中 `clamped_frames` 与 `spikes_gt_*` 并列 |
| 7 | 合成输入移入独立线程（`m0-input-selftest`） |
| 8 | 预热结束同时 `stats.reset()` 与 `input.resetStats()` |
| 9 | 对照实验：`tmp/JitterProbe.java`（纯 Java 空循环，无 GL/IO/网络，同协议）：4.25 亿采样中仍停顿 6 次 >50 ms、最大 143.8 ms → 判定环境外因 |
| 10 | 本条为文档约束，M1 报告必须显式声明"M0 FPS 不作为基线" |

### C.4′.2 环境对照实验是必备手段（条款 9 的落地要求）

**凡是要下"卡顿/性能不达标"结论，必须提供一个不包含被测对象的对照实验。**
M0 的对照组是纯 Java 空循环；M1 起如果出现"区块网格重建导致卡顿"的怀疑，
对照组应为"关闭网格重建的同一场景"。

### TR7：本机环境下"合成键盘输入"无法送达任何窗口

| 项 | 内容 |
|---|---|
| **现象** | 用 `SendInput`（走系统输入队列，与物理键盘同路径）向已确认处于前台且拥有键盘焦点的窗口注入按键，事件**不产生回调**；同一台机器上同一窗口对 `PostMessageW`（直接投递窗口过程）**完全正常** |
| **证据** | 4 轮 GLFW 窗口实验（28–44 个事件，仅 ESC 偶发到达）；**对照实验**：本进程自建 WinForms 窗口，`GetForegroundWindow` 与 `GetGUIThreadInfo().hwndFocus` **双重验证通过**，注入 8 个按键 → **收到 0 个 KeyDown** |
| **判定** | **环境约束**，非引擎缺陷。合成键盘输入在本机被拦在窗口过程之前；`PostMessageW` 通道不受影响 |
| **影响** | ① T-2 的"物理键鼠路由"只能靠**人工**或**真实键盘**闭环；② **M1 起所有交互验证必须设计为"不依赖合成输入"**（见 §T′.1） |
| **缓解** | §T′.1 的"进程内脚本化输入"方案；另：机器上真实键盘事件可正常到达（实测 `key=LEFT_ALT (342) scancode=56 mods=0x4`） |

### T′.1 由 TR7 衍生的测试策略（M1 起强制）

因为"从外部注入输入"这条路不可用，**交互功能的自动验证必须在进程内完成**：

1. **脚本化意图注入**：`PlayerIntent` 由一层可替换的输入源产生。默认源读 GLFW；
   自测模式读**脚本化的意图序列**（如"前进 2 秒 → 跳跃 → 左键按住 1.2 秒 → 右键"）。
   **被测对象是同一条游戏逻辑链路**，被绕开的只有 OS→GLFW 这一段。
2. **帧缓冲截图**：用 `glReadPixels` 从帧缓冲抓图并写成 PNG，作为可视化证据。
   这条**完全不经过 OS 输入系统**，因此在本机可用。
3. **人工 Gate 只负责"手感与可玩性"**，不再承担"功能是否存在"的举证责任。

## V′. M1.5 Front-End & Settings 的决策增补

> 本节由 M1.5 里程碑的实测与人工试玩结果收敛而来，覆盖 M1.5 及其后。
> 编号沿用 §A′/§S′/§T′/§U′ 的口径：**每一条都是"曾经踩过、下次不许再踩"的硬约束**，
> 而不是事后总结。

### V′.1 帧级输入量必须"发放"，不能被就地取走

| 项 | 内容 |
|---|---|
| **现象** | 注入 100 px 鼠标横移，视角变化在 0° 与 18° 之间随机（120 Hz 渲染 / 60 Hz 逻辑下约一半的帧读到 0） |
| **根因** | `InputMapper.poll()` 里的 `consumeFrameDelta()` **一取即清**，而主循环是"固定逻辑步 + 可变渲染帧"：一帧可能跑 **0 个**逻辑步（位移被取走即丢弃）或**多个**逻辑步（同一份位移被重复施加） |
| **规则** | **帧级量（鼠标位移、滚轮）与逻辑步粒度不同，必须显式经受一次"发放"**：每帧开始 `beginFrame()` → `accumulate(...)`；本帧**第一个真正执行的逻辑步**取走全部，后续逻辑步拿到 `withLook(0,0)` 的零值副本；菜单期间 `discard()`。**不得在帧级"取走"之后依赖逻辑步再去读** |
| **实现** | `input/FrameInputQuantities` + `PlayerIntent.withLook/withScroll`（返回副本，其余 11 个字段逐位保真） |
| **守门断言** | `FrameInputQuantitiesTest`（8 例，含"零逻辑步不丢"与"多逻辑步只施加一次"两侧）+ `PlayerIntentCopyTest` |
| **为什么 M1 没发现** | M1 自测注入的是 `PlayerIntent`（逻辑步粒度），**绕开了整个输入层**。换观测粒度才发现 —— 因此这也是一条**测试策略**约束：新增"帧粒度"输入通路（鼠标、滚轮、手柄轴）时，必须同时新增帧粒度的注入器 |

### V′.2 输入撤走之后必须收敛（"验证启动不能替代验证停止"）

| 项 | 内容 |
|---|---|
| **现象** | 人工试玩："按一下方向键之后会一直平移" |
| **根因** | `Player.applyMovementInput` 在无输入时 `return`，目标速度停在最后一次的行走速度，指数逼近永远朝它收敛 |
| **规则（硬约束）** | **任何由输入驱动的持续状态（移动、挖掘、加速、瞄准、后坐力恢复……）都必须有一条"输入撤走之后会收敛"的断言。** 只断言"输入之后发生了 X"是不完整的 |
| **阈值的写法** | 断言必须与**物理时间常数**挂钩：指数逼近是渐近的，永远不严格归零。因此"停下"要拆成两条 —— "最终会停"（`< 1e-6`）与"停得够快"（0.25 s 后 `< 2%` 行走速度）。**不得写 `assertEquals(0.0, ...)`** |
| **守门断言** | `PlayerPhysicsTest` 的 5 例松键/空中/落地/反向输入；界面自测的"松键 30 逻辑步后水平速度 < 1e-3 且滑行 < 0.4 格" |
| **同源要求** | T-8.9 的破坏反馈同理：不仅要有"按住会挖"，还要有"松手会停、裂纹会消失" |

### V′.3 失焦必须释放全部输入（GLFW 的焦点模型）

| 项 | 内容 |
|---|---|
| **现象** | 按着 W 切走窗口再切回来，角色仍在前进 |
| **根因** | GLFW 只把事件投递给**拥有焦点**的窗口：焦点离开时，RELEASE 事件会被投递到别的窗口，本进程的 `keyDown[W]` 永远是 true |
| **规则** | **`onWindowFocus(false)` 必须调用 `releaseAllInputs()`**（清空按键与鼠标键电平 + 清除**全部按下沿**）。清按下沿同样必要：否则"切走时按下的键"会在切回来时补触发一次 |
| **守门断言** | `InputStateTest`（7 例：释放 W / 释放鼠标键 / 清除按下沿 / 不失焦不释放 / 失焦保留统计 / 失焦后可再按 / 可重复调用） |
| **推广** | 任何"电平驱动"的输入（含鼠标键）都要走同一条路径，不要只处理键盘 |

### V′.4 破坏反馈是 PRD【MVP 必须】项，其实现方式受 T-8.1 约束

| 项 | 内容 |
|---|---|
| **依据** | `PRD_v0.3.1` §挖掘「破坏反馈」：**方块表面显示 10 段裂纹动画**（【MVP 必须】）；PRD 的 M1 里程碑交付内容也列有"挖掘进度与**破坏反馈**" |
| **实现约束** | 因 T-8.1 尚无 `TextureArray`，裂纹**必须**用"世界空间小四边形 + 深色 + 混合"实现，**不得**为此提前引入纹理数组，也不得改动 `voxel.vert` 的顶点格式（`aPos(vec3)+aColor(vec4)`，stride 28 B） |
| **精度约束** | 世界坐标必须拆成"整数偏移走 uniform + 块内相对量（[0,1]）"两段，与既有 `uChunkOffset` 约定一致。**顶点里不得直接写大世界坐标** |
| **稳定性约束** | 图案种子必须由方块坐标哈希得出（全整数运算）→ 同一方块图案永远一致（不闪烁），不同方块不雷同，且零存储 |
| **几何约束** | 贴面沿法线外偏 **2.5e-3 格**（防 z-fighting）；面局部坐标钳在 **[0.06, 0.94]**（防越界飘到相邻方块）；六面基必须满足 **u × v = 法线**（保证从外侧看是 CCW） |
| **状态约束** | 不写深度、开混合、**关背面剔除**（可见性由深度缓冲决定）；绕序的正确性由单测独立断言，两道保险 |
| **守门断言** | `CrackOverlayTest`（10 例：段数映射 / 退化输入 / 顶点数 / 六面贴面位置 / 绕序 / 图案稳定性 / 颜色与明暗 / 分量口径）+ 界面自测 `MINE_BY_MOUSE` 阶段（4 条断言 + 3 张取证图）+ 像素差分探针 `tmp/CrackDiffProbe.java` |
| **仍未做** | 音效与破坏粒子 → **T-8.9** |

### V′.5 表现层"画出来了"只能由像素证明，不能由断言证明

| 项 | 内容 |
|---|---|
| **现象** | 挖掘进度条与裂纹的**逻辑与提交**全部正确，断言全绿，但人工试玩仍报"没有动画" |
| **规则** | **凡"看得见的东西"（HUD 元素、覆盖层、菜单排版），断言只能证明"我提交了 N 个图元"，必须另有像素级证据。** 而在没有 OS 输入、也无法用眼睛看图的自动化环境里，像素证据的形式是**探针**：<br>① 按绘制契约的**颜色常量**扫描（`MiningBarProbe`：填充色 `(242,230,140)` / 轨道色 `(46,46,51)`）；<br>② 对**仅有一处差异**的两帧做差分 + 连通分量分析（`CrackDiffProbe`：相机与世界相同、只差裂纹段数的两帧，差出的 3824 px 必然是裂纹） |
| **为什么"仅有一处差异"是关键** | 差分只有在"控制的变量唯一"时才能归因。因此取证流程里必须安排**同相机、同世界、只差进度**的两帧 —— 这属于测试设计，不是运气 |
| **推论** | 若某条反馈无法用上述两种探针证明（例如音效），就必须**明确记为未验证**，而不是用"代码看起来对"顶替 |

### V′.6 规格覆盖度必须显式普查

| 项 | 内容 |
|---|---|
| **现象** | T-8.9 的缺口（PRD 明文【MVP 必须】）存在了整整一个里程碑，既未实现也未登记，最后被玩家撞到 |
| **规则** | **每个里程碑验收时，必须对上游 PRD 中标注【MVP 必须】且落在该里程碑交付内容里的条目做一次逐条覆盖度普查**，结论三选一：**已实现且有证据** / **已登记顺延并写明理由** / **缺口（必须在结项前处置）**。禁止出现"没做也没记"的第四种状态 |

### W′.5 中文字体技术裁决（用户裁决 B；**本轮只写方案，不实现**）

| 项 | 内容 |
|---|---|
| **背景** | `PRD_v0.3.2` 第 853 行（硬约束）：玩家可见界面文字使用**简体中文**。而 `render/ui/BitmapFont` 是程序化 5×7 **ASCII** 点阵（只覆盖 ASCII 32–126），`Menus.java` 注释原文："写中文不会报错 —— 会渲染成一串 `?`"。这是 MVP_AUDIT `DRIFT-B-04`（8 条 MVP-TEXT + SET-008 判 CONFLICT 的根因） |
| **裁决 B-1：`BitmapFont` 的去留** | **保留**，但**定位改为 `Debug / Emergency Fallback Font`**：只服务于 F3 调试 overlay、启动自检、字体系统失效时的兜底。**不再承担任何正式玩家 UI**（主菜单 / 设置 / 暂停 / HUD 文案一律不得再用它出中文） |
| **裁决 B-2：新增 CJK-capable Font Renderer** | M2 前半阶段必须建立。最低可验收要求：能正确渲染 **手枪 / 手枪弹 / 弹药不足 / 右键瞄准 / R 换弹 / 生命 / 设置 / 继续游戏 / 保存并返回主菜单** 这 9 条中文串 |
| **裁决 B-3：实现路线（硬约束）** | **不得手写几千个中文字模**。走真正的 **glyph / font atlas** 路线：优先使用 LWJGL 已随发行提供的 **`org.lwjgl:lwjgl-stb`（`stb_truetype`）**（`technical-constraints.md` 第 103 行已列为可用依赖）或等价的轻量 TTF 方案 |
| **裁决 B-4：字体系统必须具备的链路** | `Unicode code point → glyph lookup → atlas → UV → advance → baseline`。至少支持 **基本 ASCII + 本 MVP 实际用到的简体中文字形**；**本轮不要求完整中文字符全集**（不做全字库烘焙，按需取字形进 atlas） |
| **裁决 B-5：许可证（硬约束）** | 开发阶段允许使用**本机合法可访问的中文系统字体**做技术验证；**严禁把系统字体文件复制进仓库作为最终发行资产**。正式可再分发字体（OFL / Apache / MIT 一类）留到 **Content / Release 前**完成许可证确认与替换 —— 与 `technical-constraints.md` 第 973 行"只选 OFL/Apache/MIT 授权字体"同源 |
| **本轮动作** | **只登记方案，不实现**。M2 前半阶段启动时才开工；开工前 `DRIFT-B-04` 牵连的 8 条 MVP-TEXT 仍不可验收 |
| **验收方式（预先钉死）** | 中文字形"画出来了"不能由断言证明，只能由**像素**证明 —— 沿用 §V′.5 的探针口径：对渲染出的中文串做**字形包围盒 / 非空像素占比**扫描，并与 ASCII 降级渲染（`?` 串）做对照，证明"不是一串问号" |
